# 战斗协议（客户端侧）— 来自 loginp.exe 反编译

> 来源：`loginp.exe` 的战斗 C2S 构造函数 `FUN_009b6874`（0x9b6874）、S2C 分发函数 `FUN_009bc870`（0x9bc870）、
> 战斗结束判定 `FUN_009973a8`（0x9973a8）、怪物出招 AI `FUN_009a8220`（0x9a8220）、玩家点格出招 `FUN_00991d90`（0x991d90）。
> 与服务端侧旧抓包笔记（`新网金\99-历史\协议抓包-初步分析.md` 550–980 行）逐项对照过。
>
> 置信度标记：**【确】** 反编译直接读出；**【确+抓包】** 反编译与旧抓包互相印证；**【推】** 合理推断；**【未解】**。
> 本文**没有**对真实对局抓包做过验证，【确】只代表"客户端代码就是这么写的"。

## 0. 先回答服务端的三个问题

| 问题 | 答案 |
|---|---|
| **谁算伤害？** | **服务端**。客户端发的 `C2S 0xD7` 里没有任何伤害字段（只有施术者、指令类型、武功 id×100+招式序号、格子、朝向、武功等级、校验字节）。客户端里怪物 HP 只在收到 `S2C 0xD8`（实体 id + **绝对气血**）时被写入，差值（旧值−新值）仅存到 `+0x449f3` 供飘字。在 S2C 处理路径与 D7 发送路径里没有看到本地扣血代码（没做全程序穷举）。【确】 |
| **怎么触发掉落？** | 客户端**不触发**。掉落全由服务端下发：`S2C 0xE4`（在格子 (col,row) 上放物品 id）→ `S2C 0x77`（背包增物）→ `S2C 0xE8`（谁拾取了哪一格）。服务端应在**怪物气血被它自己算到 0 的那一刻**发，不要等 `C2S 0xE5`。【确+抓包】 |
| **怎么判断战斗结束？** | **客户端自己判**（`FUN_009973a8`）：按队伍统计存活者，一方清零就得出结果码，**等 ~15 秒**（演出时间）后发 `C2S 0xE5`（或 `0xE6`）通知服务端。载荷里**不含胜负结果**，服务端必须按自己持有的气血判胜负（旧抓包里 `S2C 0x81` 的 `01/02` 就是按气血是否为 0 回的）。【确】 |

另一个旧笔记没写、但对服务端设计影响很大的事实：

* **怪物的出招 AI 跑在客户端**（`FUN_009a8220`）：客户端为每只怪选目标、选招式、算朝向，然后替怪发 `C2S 0xD7`。
  这就是旧抓包里"65 个 D7 全是 C2S、其中 52 个施术者是怪"的原因。服务端要么**接受并校验**这些怪的 D7，要么自己再跑一套 AI 并忽略客户端发的怪 D7。【确+抓包】
* **旧笔记里的"类型 LE16"（2133/2324）不是类型**：`S2C 0xD5` 的每条 6 字节记录是 `实体id(LE32) + 字节A + 字节B`，
  A、B 都是**行动/动画计时初值**（见 §3），`0x0855` 只是 `A=0x55,B=0x08` 被误拼成 LE16。【确】

## 1. 约定

* **实体 id**：`< 100000000`（1e8）→ 玩家（就是 jyid）；`≥ 1e8` → 怪物实例，`id = 实例序号×100000 + mob_id`（再加 1e8 的整数倍偏移，客户端用 `(id % 100000000) / 100000` 当怪物槽位下标，用 `id % 100000` 当 mob_id）。【确+抓包】
  例：`100038166` → 槽位 0，mob 38166（倭寇）；`100138166` → 槽位 1。
* **格子坐标**：`(col, row)` 两个字节，战场格子表按 `col*0x23bec + row*0x245` 寻址。【确】
* **队伍号**：实体字节 `team`：1 = 一方，2 = 另一方，≥3 = 其他阵营（只在特殊玩法出现）。我方队伍号存在 `G+0x75`。【确】
* 下文偏移：S2C "载荷第 n 字节" 都指**去掉 opcode 后**的 0 起算下标（即客户端代码里的 `local_c[n]`）；Delphi 的 `Copy(s, k, len)` 是 1 起算，已换算。

## 2. C2S（客户端 → 服务端）

调用 `FUN_009b6874(type, mode, idx)` 统一构造；`type` 即 opcode。扫描所有调用点的结果：

| opcode | 调用点数 | 含义 | 载荷（已知部分） |
|---|---|---|---|
| `0x30` | — | 遭遇/进入战斗请求（在别的函数里发） | 实体 id(LE32) + 19 字节（旧抓包：零即可）【确+抓包】 |
| `0xE3` | 6 | **进战**（玩家入场格） | `jyid(LE32) + col + row + 1字节(01/07) + 尾字节`；col/row 来自 `G+0x29f/0x29e` 的玩家当前格，尾字节为校验（§6）【确+抓包】 |
| `0xD7` | 3（玩家 2、怪物 AI 1） | **出招**（玩家点格 / 怪物 AI） | 28 字节，见 §2.1 |
| `0xD4` | 1 | 位置/移动意图 | 目标实体 id(LE32) + 2 个坐标字节 + 1 个密钥字节 + …；旧抓包里服务端用第 6 字节异或还原两个坐标【确+抓包】 |
| `0xD8` `0xDF` `0xDE` | 2 / 3 / 10 | 战斗内的状态/行动上报（长度 14/18/26） | **【未解】**（尾部 LE32 是全场共用的单调 tick） |
| `0xE5` | 1（`FUN_009973a8`） | **战斗结束上报（情形 A）** | 反编译里是"校验字节 + LE32 计数 + 尾字节"三段拼接，顺序没完全看清；服务端侧旧实测是 `jyid(LE32) + 1 字节`，jyclient 按后者发。见 §5、§6 |
| `0xE6` | 1（同上） | **战斗结束上报（情形 B）** | 同上结构 |
| `0xE4` `0xE7` `0xE8` `0xEC` `0xED` `0xEE` | 3/2/3/6/1/1 | 战斗内道具/特殊动作类 | **【未解】** |
| `0xD3` `0xD6` `0xD9` `0xDA` `0xDB` `0xE2` `0xF1`–`0xF6` `0xF9` | 若干 | 战斗初始化/各玩法分支 | **【未解】** |

另有少数分支（特殊玩法 mode `0x13` `0x1f` 等）用 **十进制文本**拼指令走 `FUN_009db454`（文本通道）而不是二进制 `FUN_009cb16c`，网页端第一版可以不管。

### 2.1 `C2S 0xD7` 出招（28 字节）【确+抓包】

```
+0   LE32  施术者实体 id（玩家=jyid；怪=怪实体 id）
+4   BYTE  指令类型：2=攻(基本功) 3=武(门派武功) 5=特(毒等) …   ← 同时写进客户端实体的"当前动作"字节(+0x25d)
+5   BYTE  1/2   （怪恒 1）                                    【未解】
+6   LE32  武功 id×100 + 招式序号   （G.d0x2ec；基本功=8003xx/8012xx）
+10  BYTE  怪恒 5，玩家见过 0/3                                【未解】
+11  BYTE  col  = G.b0x290  ：移动终点/出招落点格（近战=自己所在格）
+12  BYTE  row  = G.b0x28f
+13  BYTE  = G.b0x2a9 ：**混淆过的**点击/目标格 col
+14  BYTE  = G.b0x2a8 ：**混淆过的**点击/目标格 row
+15  BYTE  朝向（G.b0x28e，由两点坐标算出的方向，0–7）          【推】旧笔记猜"队列位"，更像 8 向朝向
+16..20  00
+21  LE16  战斗内 tick（全场共享单调递增）
+23,24  00
+25  LE16  该武功当前等级（基本功恒 0）
+27  BYTE  尾校验字节
```

* **`+13/+14` 的谜底**：玩家发的 `+13/+14` **不是格子**，是混淆值：
  `b2a9 = ((jyid + SEED + 0x0B) % 100) XOR 点击col`，`b2a8 = ((jyid + SEED + 0x17) % 100) XOR 点击row`，
  其中 `SEED = G.dx024d8197`（进战后客户端持有的一个会话值）。**2026-10-19 逆向确认：SEED = S2C `0xD1` 载荷偏移 16 的 LE32（就是服务端发的那个 1–100 随机数）**：
  处理函数 `FUN_0062c0c8`（0x62c0c8，Delphi 字符串解析，`Copy(s,0x11,4)`→`FUN_00534f68` 转整数）把它连同 `Copy(s,3,4)`=实体 id、`Copy(s,0x15,2)`=场景索引等字段一起传给 `FUN_006c4610`（0x6c4610），后者在 `0x6c4c39` 写入 `G+0x24d8197`。
  所以服务端要还原玩家点击格：`col = b2a9 ^ ((jyid+SEED+0x0B)%100)`、`row = b2a8 ^ ((jyid+SEED+0x17)%100)`。`jyclient.fight_act` 已按此发送。
  D1 里偏移 20 的 LE16 = 场景索引（旧抓包恒 0），`FUN_006c4610` 用它查一张场景表（取 +0x0c/+0x0e/+0x12/+0x1c/+0x20/+0x24 等字段）。
  这就是旧笔记里"玩家的 `[13,14]` 取值超出格范围（53,46)(65,127)"、"跨战斗偏移不一样"的原因。
  **怪**发的 D7 则直接是目标格（旧抓包 150/150 命中），因为怪的 AI 路径不做混淆。
* 对新服务端：**不必还原** `+13/+14`，直接用 `+11/+12`、武功 id、施术者就够模拟；校验类字节可以先不验。

## 3. S2C（服务端 → 客户端）

分发函数：`FUN_009bc870(type, payload)`，处理 `0xC6–0xFE` 区间，**每包进来都先置 `G.b0x43=0`、`G.x024d6271=1`**（刷新标志，处理完部分分支会再置 1 触发重绘）。

下表"载荷"是 0 起算下标（去掉 opcode）：

| opcode | 含义 | 载荷 | 客户端做什么 |
|---|---|---|---|
| `0xC6` | 战斗心跳/就绪 | 空 | 若 `G.d0x4a == jyid`：置 `b0x44=1`（可以出招）、刷新计时 |
| `0xD3` | 战斗场景布置/位置初始化 | 282 行分支，含 `[4][5][6]` 与 4 字节 id | **【未解】**（大分支，疑似建场景/站位） |
| `0xD4` | **怪物移动/位置广播** | `id(LE32) col row [dirOrSpeed]`（7 字节时多一字节） | 找到该怪槽位，把怪从旧格移到 (col,row)，设置"正在走动"，重算像素坐标与朝向；`b1346c9=1`【确+抓包】 |
| `0xD5` | **参战名单** | `count(LE16)`，随后 `count × [id(LE32) A(1) B(1)]` | 对怪（id ≥ 1e8）：`A`→怪的行动计时初值(`+0x44cb4`，另存 `A+随机0–1秒` 为"下次行动时刻")，`B`→怪的动画/朝向初值(`+0x44b9f`)；对玩家走另一分支（队伍/观战）。服务端连发两个：先我方后敌方【确+抓包】 |
| `0xD6` | 状态列表 | 变长，记录步长未确定 | **【未解】** |
| `0xD7` | **出招转发（动画触发）** | 同 C2S D7 的**前 16 字节**：`id(4) cmd(1) b5(1) skill*100+idx(LE32) b10 col(1) row(1) tcol(1) trow(1) dir(1)` | 把 `cmd` 写入该实体当前动作（`0x10` 被改成 3），写技能、两个格坐标、朝向，播放出招动画。**不含伤害**【确+抓包】 |
| `0xD8` | **气血广播（绝对值）** | `01`(1) + `N × [id(LE32) HP(LE32)]` | 怪（id ≥ 1e8）：若 HP>0，写 `+0x4490e=HP`，`+0x449f3=旧-新`，置 `+0x44968=1`（需刷新血条/飘字），并标志"气血下降(+0x44969)/上升(+0x4496a)"。HP=0 即视为死亡。对玩家：多数模式只在 `0x7B` 子类型 `0x18` 里更新（D8 里玩家分支仅个别玩法用）【确+抓包】 |
| `0xD9` | 状态/效果列表 | 记录含 id + 一个 4 字节值 | **【未解】** |
| `0xDB` `0xDD` | 状态列表（含若干 LE16） | 同上 | **【未解】** |
| `0xDC` | **参战实体初始数值** | `count(LE16)` + `count × 21 字节`：`+3 id(LE32)`、`+7 LE32(=1)`、`+11 LE32 气血`、`+15 LE16`、`+17 LE16`、`+19 LE32`（以 count=1、总长 23 的抓包样本推断步长 21）| 建立实体的血条基准【确 + 步长【推】】 |
| `0xDE` | 单字段通知 | 含 `[4]` | **【未解】** |
| `0xE0` `0xE1` `0xE2` `0xE3` | 战斗内状态/特效类 | | **【未解】** |
| `0xE4` | **掉落：在格子上放物品** | `N × [col(1) row(1) item(LE16)]`（步长 4） | 把 item id 写入格子表 `(col,row)`，刷新显示；之后 `G.x024d827f=1`。旧笔记"句柄"其实就是**格子坐标**【确】 |
| `0xE5` | 实体特效/招式状态 | `id(LE32) +4 字节？ +LE16(×100+1 = 技能号) +…` | 给实体设置当前技能号与特效；若首次触发创建特效对象【确，含义【推】】 |
| `0xE6` | **实体离场**（死亡/逃跑/战斗结束） | `id(LE32)`（若长度>4 且实体是自己 = 整场结束） | 找到实体，清它的槽位、停动画；玩家 id 命中则 `b0x3c=1`；`len>4 && 是自己位` 时复位战斗全局状态（`b0x45=1,w0x40=0,x024d628a=6…`）；最后 `b1346c7=1` 通知结算界面【确+抓包】 |
| `0xE7` | 朝向更新 | `N × [id(LE32) dir(1)]` | 写实体朝向字节（`+0x28e` / `+0x44b4c`）【确】 |
| `0xE8` | **拾取：某实体拾走了某格的物品** | `id(LE32) col row` | 取格子表 `(col,row)` 的物品，聊天栏提示"X拾获Y"（自己 id 才提示，战场类 mode 也给别人提示），清空该格【确】 |
| `0xE9` `0xEA` | 大分支（含多个 id / 数值） | | **【未解】** |
| `0xEB`–`0xFE` | 其余 | | 其中 `0xEF`（每场 3–9 次，`jyid(LE32)+1字节 0x48/0x54`）**【未解】**；`0xF0` `0xF2` `0xFA` `0xFB` 为 id 列表，`0xFE` 单 id |

另外在**别的处理器**（不在 `0xC6–0xFE` 区间）里处理的战斗相关包：`0x81`（战斗结算：`01`=我方存活、`02`=气血为 0）、`0x82`、`0x7B`（属性更新；子类型 `0x18` 气血）、`0x77`（背包加物品）、`0xD1`（遭遇应答，24 字节，随机数 LE32）。`0xD1` **没有**出现在 `0xC6–0xFE` 分支里，其处理函数**【未找到】**。

## 4. 实体记录与关键字段（客户端内存，供还原 UI 用）

* 每个战斗实体记录 0x463 字节，**三组数组同一布局**（基址 = "present"字节）：`G+0x45…`（玩家，数量 `b1346cc`）、`G+0x44903…`（怪物槽位，下标 = `(id%1e8)/1e5`）、`G+0x8c1b5…`（汇总，供结束判定统计，数量 `b1346cd + b1346ce`）。
* 记录内偏移（由反编译里的绝对地址换算，基址 = present 字节）：`+0x00 present`、`+0x05 id(LE32)`、`+0x0B 气血(LE32)`、`+0x30 队伍号`、
  `+0x66 气血下降标志`、`+0x67 气血上升标志`、`+0xF0 本次降幅(旧-新)`、`+0xEF 已逃跑`、`+0x2DA 状态(0/2=在场，其它=倒下)`、
  `+0x218 当前动作类型`（来自 D7 的 cmd）、`+0x249 朝向`、`+0x259 row`、`+0x25A col`。
* 战场格子表按 `col*0x23bec + row*0x245` 寻址；已确认的格内字段只有：`LE16 物品 id`（掉落，E4 写入、E8 清空）、`LE32 像素 x`、`LE32 像素 y`。可走/占用标志存在别处，**【未解】**。

## 5. 战斗结束判定（`FUN_009973a8`）

触发时机：`G.b0x3f != 0`（上一次事件置位）**或**距上次判定 > 5 秒。每次：

1. `FUN_0099d5d8` 统计存活：实体 `present≠0` 且 `escaped(+0xEF)==0` 且 `state(+0x2DA) ∈ {0,2}`（模式 `1399e3==1` 时还要 HP>1），按 `team` 累计：`cnt[0]=team1 人数`、`cnt[1]=team2 人数`、`cnt[3]` 其它队同号、`cnt[2]` 其它队。
2. 按玩法 mode（`G.x024d6277`）和各种附加条件（胜利/失败目标怪 id、倒计时、目标格到达、某怪 HP ≤ 阈值……）得出结果码 `G.w0x40`：

| 结果码 | 含义 | 主要触发 |
|---|---|---|
| `0x16`(22) | **我方胜** | 敌方队伍存活数=0（"我方 team=2 且 cnt[0]==0" 或 "team=1 且 cnt[1]==0"） |
| `0x0B`(11) | **我方败** | 我方队伍存活数=0 |
| `0x01` | 本人倒下（HP<2，或特殊模式） | `G.d0x50 < 2` |
| `0x03` | 本人不在场/观战 | |
| `0x06` | 逃跑/退出 | 触发 `FUN_00993650` |
| `0x21`(33) | 特殊 | |
| `0xDE`(222) | 特殊模式下的胜 | `G+0x124f4e≠0` 时把 22 改成 222 |
| `+100`/`+1000` | 特殊模式（+100）；已上报标记（+1000） | |

3. **上报**（等待 ~15 秒，结果 6/33 立即）：
   * 结果 ∈ `{6, 11, 22, 101, 111, 222}`，且 mode ∉ `{5,7,11,13,15,19–29}`，且"只有我方队伍有真人参战"（`FUN_009972e4`：`G+0x1346c4/5/6` 三个队伍真人计数里，只有自己所在队非零）→ 发 **`C2S 0xE5`**；
   * 否则结果 ∈ `{3, 6, 22, 33, 101, 111, 222}` → 发 **`C2S 0xE6`**。
   * 发出后 `w0x40 += 1000`，防重发。
   * 结果码 `1` 与 `11` **不上报 E6**；`11` 只会走 E5。
4. 服务端的回应（旧抓包）：`S2C 0x81(01|02)` + `0x82` + `0xE6(jyid)` + `0x7B 18`（恢复气血）。**客户端在收到 `S2C 0xE6`(自己) 才真正复位战斗状态。**

> 含义【推】：`E5` = 单人（或只有我方真人）的 PvE 结算上报；`E6` = 多队真人/PvP/其它玩法的结束上报。
> 服务端若第一版只做单人打怪，只需实现 E5 路径。

## 6. 反作弊字节（服务端可先不验）

* 所有战斗 C2S 的**尾部校验字节**都是 `FUN_009b6798(表下标)` 取自一张字符表（`PTR_DAT_00a26304` 指向的表长），下标 = `(某会话常量 + 魔数 + 若干状态字节…) % 表长 + 1`。魔数每个 opcode 不同（`0xE3`: `d0x4a+0x1403+b29f+b29e−2·b28e`；`0xE5`: `FUN_009c7d60(...)+0x3039`；`0xE6`: `+0x7B`；…）。
* 另有一个"计数器"LE32：`计数器 = 时钟(FUN_009c7d60) − 0x32·G.d0x1346a8 − 0x14·随机 − (随机&0xff)`，服务端旧版用它检测"开快招/快速集气"（攻击间隔 < 0x514）。
* 校验的**原值**客户端是知道的，但服务端要还原得知道 `SEED`（`G.dx024d8197`）和字符表内容。**建议新服务端第一版全部不验**，只取业务字段。

命令号 = 命令表下标（1 移動 2 一般攻擊 3 特殊攻擊 4 暗器 5 毒術 6 醫療 7 防禦 8 閃躲 9 養精蓄銳 10 逃跑 11 自動 12 裝備 …），`G+0x25d` / D7 的 cmd 字节也是这个值。**新服务端目前没有 `0xDE` / `0xF9`**（`opcodes.py` 里没有），需要服务端会话补：收到 `0xDE` 回 `D7` 转发；收到 `0xF9` 按"此处能不能逃"决定结束战斗（`81` + `E6` 自己 + `7B 18`）。客户端侧见 `jyfight.build_pose / build_escape`、`jyclient.fight_pose / fight_escape`、网关操作 `fight_pose / fight_escape`；`combat_server.py` 里有一个假的应答（逃跑一律成功）。

**服务端已实现（2026-10-20，见服务端 `docs/战斗.md`）并由客户端接上**：
- C2S `0xDE` → 回 S2C `D7`（`jyid + 命令号 + 11 个零`，自拟）。真原版对校验字节不对的 `0xDE` 一律静默，所以这条在原版服务端上我们现在的客户端发不出有效包（校验字节没解，客户端发 0）。
