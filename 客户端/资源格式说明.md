# 《金庸群侠传》(网金) 旧版客户端 资源文件格式说明

范围：`客户端\share` 下的 role / pic / mainpic / FightPic / FightDat / dat / cursor / sound / font / prlfile / rol，以及 `maina` 下的 CSV。
方法：先用十六进制 + 统计 + 渲染验证，卡住的地方（`.cp` 帧压缩算法）到 `loginp.exe` 里找到加载函数确认（REA/Ghidra，没有运行客户端）。
转换器：`逆向工具\资源解析\wjres.py`（Python 3 + Pillow，只读输入，不改原始文件）。

标记：**[已验证]** = 用该规则解出的图片/数据肉眼或数值核对过；**[推测]** = 只有字段形态上的猜测；**[未解]** = 只有文件头特征。
所有整数都是小端。RGB565 指 `r5 g6 b5` 的 16 位像素（`v>>11` 为红）。

---

## 1. .mrg 容器 [已验证]

`share` 里 90% 的图片/声音资源都装在 .mrg 里（`role\*.mrg`、`pic\*.mrg`、`FightPic\*.mrg`、`sound\*.mrg`、`dat\Scene6.mrg`、`dat\Seabk.mrg` 等；`pic\textMrg.txt` 其实也是 .mrg）。loginp.exe 里读取它的类：`FUN_004bb2a4`(打开) / `FUN_004bb3a8`(读记录) / `FUN_004bb488`(定位记录)，记录表项每项 `0xd` 字节，与下表一致。

```
偏移          大小          含义
0             u32           count，记录数
4             u32           namesLen，名字表字节数
8             count * 13    记录表，每项：
                              +0 u32 size    记录字节数（可为 0 = 空记录）
                              +4 u32 offset  记录在数据区内的偏移
                              +8 u32 0       (恒 0；疑似 offset 的高 32 位)
                              +12 u8 type    0 或 6，含义见下（不影响数据解析）
8+13*count    namesLen      名字表：GBK 文本，每个名字以 \r\n 结尾（count 项）
8+13*count+namesLen         数据区起点 base；记录 i 的数据 = file[base+offset : base+offset+size]
```

* 名字：role 里是原作者的路径+文件名（如 `ROLE\M1MA01.CP3`、`role\41174.cp`），pic 里是资源名（`bm11001`、`selrect01`、`0007`…），名字可重复。
* `type` 字节：role 全是 0；pic 里出现 0 和 6（`add100/101.mrg`、`FlashPic*`、`GenGame`、`Pan_Com12` 全是 6，其余基本是 0）。6 与 0 的记录用同一套解码规则，**用途不明 [未解]**，可能是"加载策略/是否常驻内存"。
* 文件尾无校验。空文件（`boy09.mrg`、`girl08.mrg`、`SeaBK1.mrg`，8 字节全 0）= count 0。
* 记录的内容靠头部特征区分，见 §2–§6。converter 的判定顺序：JPEG(`FF D8`) → RIFF → 裸 RGB565 → rle6 → cp → `568D0F20` 压缩块 → 未知。

## 2. 记录内容类型

### 2.1 JPEG [已验证]
记录就是完整 `.jpg`（`FF D8 FF E0 … JFIF`）。用于大背景：`pic\SceneBG*.mrg`、`Pan_J*.mrg`、`YenGB*.mrg`、`newinfo*.mrg`、`smlanti.mrg`、`hp_jpg.mrg`、`add*.mrg`/`items.mrg` 中的一部分（与同包里的 raw565 配对：同名 `bm…` 是图，`…` 是 jpg，可能是图标/带 alpha 的 jpg 遮罩，**[推测]**）。直接另存为 `.jpg`。

### 2.2 RIFF/WAV [已验证]
`sound\*.mrg`、`pic\Laba.mrg`：记录就是 `RIFF…WAVE` 完整文件，直接另存 `.wav`。

### 2.3 裸 RGB565 位图 [已验证]
两种头：
```
A: u32 w, u32 h, w*h*2 字节 RGB565              (size == 8+2wh)  例: pic\items.mrg 的 bm11001(36x36), BWFire, mask, add*
B: u32 w, u32 h, u32 bytes(=2wh), 数据           (size == 12+2wh) 例: pic\menu*.mrg, rtmenu*.mrg, smap.mrg, Dota*
```
透明色：RGB565 值 **0x0000(纯黑) 当色键** [已验证：图标黑边正确去掉]。

### 2.4 "rle6" 带调色板的 RLE 位图 [已验证]  ← pic 里最常见（Scene*/KongFu*/ItemNpc*/Pan_Com*/FlashPic*/YenGame*…）
```
+0   u32 w            图像宽
+4   u32 h            图像高
+8   u32 cw           单元格宽 (精灵表里一格的宽; 整图时 cw==w)
+12  u32 ch           单元格高
+16  u32 P            调色板字节数 (偶数, ≤512; 常见 0x1fe=255 色, 也有 10/464 等)
+20  P bytes          调色板: P/2 个 u16 RGB565；索引 0.. 依次对应
+20+P u32 S           像素数据字节数 (== 记录剩余长度)
+24+P S bytes         逐行 RLE，共 h 行，每行恰好铺满 w 个像素：
        读一个字节 c：
          c != 0 : 后跟 1 字节 idx，输出 c 个像素 idx（游程）
          c == 0 : 本行剩余 (w - x) 个像素以字面量索引字节紧跟其后（无长度字段）
```
* 透明：调色板颜色为 0x0000 的索引当透明（Pan_Com 里透明索引是 231，Scene/Aspect 里是 0）[已验证，渲染正确]。
* `cw,ch`：`pic\Pan_Com.mrg` 的 `1100` 是 96x144 的 8x8 精灵表，cw,ch=12,18；Flash 动画条 `FlashPic01` 是 180x4140 的竖条(cw=180,ch=4140)。**网页端需要按 cw,ch 切格；单元格排布 = 行优先 [推测]**。
* 例外：`pic\textMrg*` 等不是图。
* 已用本规则**无错**解码的全部记录：pic 下所有 `rle6/*`（Scene2..12, ScenePic, KongFu*, ItemNpc*, Pan_Com*, YenBoat/YenGame*/YenShip*, FlashPic*, Aspect, Catch*, hp_bmp, EP15, Fight*…，共约 1 万条）、FightPic\*.mrg 全部。

### 2.5 ".cp" 多帧精灵（人物/NPC/武器特效） [已验证]  ← role 里全部 + pic\npc14.mrg
```
+0     u32 n               帧数 (含未使用的空帧)
+4     256 * u16           本记录自带的 256 色 RGB565 调色板（索引 0=黑=透明）
+516   n * 12              帧表，每帧：
                              +0 i16 ox, +2 i16 oy   帧左上角相对锚点（人物脚下/中心）的偏移（常为负）
                              +4 u16 w, +6 u16 h     帧尺寸
                              +8 u32 end             该帧压缩数据"累计"结束偏移（相对帧数据区起点）
                           未使用帧：w=h=end=0
+516+12n  帧数据区：帧 i 的压缩数据 = [end(i-1), end(i))，LZSS 压缩（见 §3），
                       解压后正好 w*h 字节，是调色板索引，逐行从上到下
```
* 帧表结构来自 loginp.exe `FUN_0051fa4c`：先读 4 字节 n、`0x200` 字节调色板、`n*0xc` 字节帧表，再对每帧调用 LZSS 解压到 `sum(w*h)` 的缓冲 [已验证]。
* 色键：调色板颜色 0x0000 当透明。
* `*S.CP*`（B10S/G10S…）是阴影层，调色板只有 `0x1863`（深灰），应半透明叠加 [推测，converter 默认 alpha=128]。

role 文件的命名与分层（以 `boy01.mrg` 为例，98 条记录）：
| 名字 | 说明 |
|---|---|
| `B10S.CP1..7` | 阴影，7 个动作/朝向组 |
| `M10000.CP1..7` | 裸体身体（皮肤） |
| `M1MA01 / M1MB01 / M1MC01` | 发型/头部 (M=男, H=head 类，**[推测]**) |
| `M1PA01..PD01` | 衣服/外装层(P) |
| `M1WA01..WE01` | 武器层(W) |
| 后缀 `.CPn` | n=1..7，7 组动作或方向；每个 .cp 里有几十~一百多帧（boy01 的 CP1 有 64 帧，CP4 有 120 帧）。**各组对应的动作、帧顺序 = [未解]**（网页端要还原动画需要找 loginp.exe 里的动作表，后续工作） |
| `girl*.mrg` | 同上，前缀 G；`npc*.mrg` 里是 `role\41174.cp` 这类单文件，一般只有 1 帧（雪人那种场景物件）或几帧 |

分层叠放：把各层同一帧 i 按 `(ox,oy)` 叠到同一锚点，顺序 阴影 → 身体 → 衣服 → 头发 → 武器（用 `boy01 CP4` 帧 0 试过，各层位置对得上；层序未对照游戏截图，**[推测]**）。

### 2.6 压缩块 `568D0F20` [已验证容器 / 内容未解]  ← `pic\EvtMrg*`、`NpcMrg*`、`MapMrg*`、`mapMrg`
```
+0 u32 0x200F8D56   魔数（字节 56 8D 0F 20）
+4 u32 L            解压后长度
+8 ...              LZSS 数据 (§3)；loginp.exe FUN_004a7f50 在发现该魔数时跳过前 8 字节
```
解压后（L 字节全部核对）：
* `NpcMrg*.Mrg` 记录：`08 "0002.wsg" 'ap'…` 形态的定长表（Pascal 短字符串 + 定长字段），按地图编号 `0002/1000/0008/0064` 分文件 —— NPC 在场景里的摆放表 **[推测]**。
* `EvtMrg*.Mrg` 记录：`c5 01 00 00 06 b7 73 a8 c6 a5 f3 …` = u32 + Pascal 字符串(Big5 "事件名") 的重复结构 —— 场景事件表 **[推测]**。
* `MapMrg*.Mrg` 记录(445247 字节一条)：开头 `86 00 64 00 01 01 | 1e 0c 00 00 2e | 1e 06 00 00 2e …`，`0x86=134, 0x64=100` 很像 **地图宽高 134x100**，后面是 5 字节一格的重复结构 `{a,b,0,0,2e}`（b 在 0..0x0d 变化）—— 地图格数据(地块/障碍/高度层) **[推测，未对照游戏确认，要进一步需要读 loginp.exe 的地图渲染]**。
`wjres.py --dump-chunks` 会把它们解压成 `.bin` 放到 `chunks/`。

### 2.7 `pic\textMrg.txt` / `TextMrg*.mrg` [未解]
`pic\TextMrg.mrg` 与 `textMrg.txt` 是同一个文件（2109147 字节，字节相同），.mrg 容器里只有 1 条记录 `TEXT`（2109120 字节）。记录头 `b4 17 1e 00 | 7c 4b 18 00 | ec c9 00 00 | 11 27 00 00 4a 00 00 00 00 00 12 27 00 00 14 00 4a 00 …`：前 12 字节像 3 个长度/偏移；其后是 `u32 id(0x2711=10001,10002,…)` 递增的定长记录，疑似文本库（对话/物品说明，Big5/GBK）。`TextMrg1.Mrg` 里的 `TEXT4`（61 字节）以 `1f 8b 08` 开头 = **gzip**，说明部分文本块用 gzip。解析需继续。

## 3. LZSS 算法 [已验证] （loginp.exe `FUN_004a7f50`）

标准 Okumura LZSS，参数：
```
环形缓冲 4096 字节，初始全部 0x20，写指针 r = 0xFEE
每 8 个单元一个标志字节，从最低位开始：
  bit=1 : 读 1 字节原样输出，写入环形缓冲[r++]
  bit=0 : 读 2 字节 b1,b2；pos = b1 | ((b2 & 0xF0) << 4)；len = (b2 & 0x0F) + 3；
          依次输出环形缓冲[(pos+k) & 0xFFF]（同时写回环形缓冲[r++]），k=0..len-1
输入读完即结束
```
（`wjres.py` 里的 `lzss()`。）

## 4. 调色板 .pal [已验证] （role\*.pal）

```
重复的块，每块 3079 字节：
   u8  nameLen (=6)
   nameLen bytes  块名，如 "m1ma01"（对应 mrg 里 M1MA01.CP* 那几条记录，不分大小写）
   3072 bytes     = 6 套 * 256 个 u16 RGB565
```
* 块数：boy01=12, boy05=13, boy10=6 (文件大小 = 3079 的整倍数，核对通过)。
* 第 0 套 **与 .cp 自带调色板完全一致**（M1MA01/M1PA01/M1WA01/M1WE01 核对 256/256 项相同），第 1..5 套是"换色"（染色/稀有度配色）版本；索引含义不变，只替换颜色。
* 对应关系：`boyNN.mrg` ↔ `boyNN.pal`，`girl.pal`↔`girl.mrg`，`girl2.pal`↔`girl02.mrg`，`girl3.pal`↔`girl03.mrg`。没有 .pal 的 mrg 只有第 0 套。
* 网页端：把 .cp 帧存成索引图，运行时换调色板最省；`wjres.py --variants N` 另外直接输出换色图集。

## 5. 光标 / 动画光标 [已验证：就是标准格式]
* `cursor\*.cur`：标准 Windows CUR（`00 00 02 00 01 00 30 30 …`，48x48，8bpp）。
* `cursor\*.ani`：标准 RIFF `ACON` 动画光标（`52 49 46 46 … 41 43 4f 4e 61 6e 69 68`）。
可直接用 Windows/浏览器工具转换，不必自定义解析。

## 6. 字体 .JPC / .TWN [已验证位图格式，字符索引表未解]
* 全部字节 **XOR 0x58**（背景 0x58 = 全 0）后是 1bpp 点阵。
* `TATPC1.JPC` (419850 字节)：前 `256*15 = 3840` 字节是 256 个 **8x15** 半角字形（含 CP437 笑脸等，ASCII 在对应码位）；之后每字 **30 字节 = 16x15**（每行 2 字节，高位在左），顺序是 **Big5 内码顺序**（渲染后第一个字是"一乙丁七乃九了二人…" = Big5 0xA440 起）。字数 (419850-3840)/30 = 13867。
* `TATPC1.TWN` (421140) 同结构，多 1290 字节（43 个 16x15 字形），可能多了符号区。
* `TATPC2.JPC/.TWN` (1010712 字节，两者同长)：字形较大，每行 2 字节，字形字节数 [未解]（1010712 = 2³·3·23·1831），**尚未确定尺寸**（可能是 16x24 或 12x? 的大号字），.JPC 与 .TWN 逐字节不同，大概是日文/台湾字集版本。
* 码位→字形偏移的映射 = Big5 低字节 0x40–0x7E,0xA1–0xFE（157 列）线性排列的推测，没有逐字验证。

## 7. maina 下的 CSV [已验证：普通文本，GBK]
* `MAP.csv`：`场景ID,x,y,名称`（"2800,1825,893,京城下雨"）；按 `1生产常用`、`1实战打点` 之类的 `序号分组名` 行分段，用于小地图/传送坐标点；末尾逗号补齐到 6 列。
* `商城.csv`：`ID,中文名,价格`（65102,帮主举荐令,999）。
* `兑换.csv`：`序号,需要物品(id:数量;…),兑换物品id,说明,商城点数`。
编码 GBK（`\xca\xb5…`），行尾 CRLF。

## 8. 其余格式（部分已解）

### 8.1 `pic\*.Pos` + `pic\*.Pak` 界面布局包 [部分解]
* `Com.Pos` / `Comt2.Pos`：8 字节头 `u32 2000(0x7d0), u32 0`，之后 N 个 `{u32 id, u32 end}`，`end` 是累计末偏移（134,318,502,…）。`Com.Pos`(8856 字节) 正好 = 8+1106*8，**只有索引**，数据在 `pic\S0.Pak`（Com.Pos 最后一个 end=247084，S0.Pak 总长 247218=247084+134，说明条目 i 的数据 = S0.Pak[end(i-1):end(i)]，**首项从 0 起**）。`Comt2.Pos` 同理对应 `S02.Pak`。id 从 3200(0xc80) 起。
* `*.Pak` 的每条记录：`u8 nameLen + 名字("s1.bmp")` + 一段**作者机器上的原始路径**（Big5 "…\桌面\…\pic\s1.bmp"，定长填 0）+ 固定头 `u32 id(与 .Pos 的 id 相同,如 0xc80)`、`u16 x, u16 y, u16 w, u16 h`（如 `60 00 90 00 30 00 60 00` = 96,144,48,96）、`ff 00 ff ff`、`u16 …`，之后是一串 0/1 字节（疑似点击热区/掩码）。**这是界面控件的位置 + 热区定义，不是图片**；`S0.Pak` 里搜到的 150 个 `BM` 多半是巧合。字段尚未逐项确认 [推测]。
* `pic\Kun_Kbjs.pkb` / `Pan_Kbjs.pkb`：9 字节一条的重复记录 `{u16 id, u8 a, u8 b, u8 0x10, u32 id}`（`01 00 01 01 10 01 00 00 00`、`02 00 01 01 10 02 00 00 00`…），后面接 `bd 01 00 00 de 03 …` 形态的 u32 序列，末尾 8 字节 0。像"门派/武功栏位表" [推测]。
* `pic\Kun_Kcbs.pkb` / `Pan_Kcbs.pkb`：`u32 count(77 / 159)`，一个 `00`，然后 count 个 `u32` 记录长度（`0x37,0x37,…,0x42,…`，Pan 版 `0x2c,…,0x63`），其后是变长记录，每条以 `u16 len(与表项一致,如 0x43)` 开头，内含 Big5 字符串（如 `b3 f2 b4 d1 bd 4c`）和 `u32` 编号序列。= 招式/门派表 [推测]。

### 8.2 `dat\*.tbl` [部分解]
`dthing.tbl`…`dthing6.tbl` 各 48000 字节 = **500 条 × 96 字节**。记录头：`u16 id(0x7dc9,0x7dca,…连续递增) + u8 + u8(=02/05) + u32 值(如 250,200,720)`，之后零，偏移 16 处还有一个 u32。大部分是 0 (熵 0.1)。看起来是物品/掉落/"东西"价格表 [推测]。

### 8.3 `prlfile\*`、`FightDat\*` [部分解]
* `Btn123456.prl` (288) / `FightDat\btdefine.dat`、`Button.dat` (176)：`u32 0x1e240(=123456，文件名里的"123456") / 0x3fc, u32 0` + 若干 `{u32 x, u32 w}`（`117 01 00 00 | 57 00 00 00` = 279,87；`14b|56`=331,86…）→ 一排按钮的 (左,宽)。`MoneyBtn*.prl`(32) 同形。
* `gn3000012345*.prl` (1092 字节)：全是 0/1 字节，1092 个开关位（`01 01 00 01 …`）。
* `Menu*.set`(4 字节 0)、`music*.set`(22 字节 0)、`sc000*.scs`(16 字节 0)：玩家本地设置存档的初始空白（音量/菜单/…开关），文件名里的数字串 `123456`、`1234567` 是账号名占位。
* `prlfile\ztnuocca.dat`：文件名是 `account` 倒写；内容是 CRLF 文本：首行数字，后面若干行账号名（登录器记住的账号列表）。含个人数据，不要提交。
* `bk0001234567.txt`、`bk0000123456.txt`：0 字节。

### 8.4 `dat\*.dat` / `FightDat\*` 数据库表 [未解，仅列特征]
共 107 个，来自服务端同款数据表。共性：
* 多数文件开头是 **`u32 记录数 + u32 + u32 …`** 一类的小头（`KKF.dat`: `0f 03 00 00 | 6a 18 00 00 | 2f 09 00 00`、`WSG*.dat`: `9e 02 00 00 | e6 0f 00 00 | 17 34 00 00`、`Item*.dat/Npc*.dat` 前几百字节全 0），随后是以 0 为主的定长记录（熵 1~3）。
* 夹杂 **Big5 字符串**（`b4 bc a4 4f a4 6a ac 44 be d4` 等，Pascal 长度前缀：`ActProtals_tw.dat: 0c 00 00 00 01 0a b4 bc a4 4f…`、`Store_tw.dat: 04 00 00 00 02 00 00 00 04 aa 5a be b9`）。
* `Bomb1..5.dat`(12000)：3 字节 `{x,y,z?}` 重复 `01 56 39 00 | 01 56 2d 00…` 4 字节一条，轨迹坐标表。`NpcRace1..3.dat`(24000)：同形 `01 44 4e 00`，赛跑 NPC 路线点。`CartPath/cartroot/cartsta/nCart*.dat`：矿车/运镖路线。
* `Drama.dat`(5.1MB)、`DelTask.dat`(22000)、`SeaBK1.dat`、`9857.sbk`(38400，几乎全 0)、`SuitStone.dat`：零占比 ≥98%，稀疏定长表。`Drama.dat` 记录里夹有 Pascal 字符串 `06 "scene1"`。
* `GHelp2.dat`、`MedFall.dat`、`lightqa.dat`、`LightQAs.dat`、`Active.dat`、`HappyYear.dat` 等的字符串部分字节分布均匀，不是 Big5 明文 —— 可能有 XOR 等轻度加密（尚未找到密钥）。`GHelp.dat`、`newbie.dat`、`snowlen.dat` 是明文文本（`*101\r\n…`、`14\r\n#…`、`{105,117,120,…`）。
* `server.dat` (47 字节)：**除末尾 CRLF 外整体 XOR 0x9c** 后即 `server.ini` 同类文本（`<服务器名> <host>*<ip>`）。[已验证]
* `FightDat\RandomTab.Dat`(65536)：65536 个均匀分布字节 = 战斗随机数表；`Hurt.Dat`/`Weight.Dat`(各 2048) 近全 0 的 256 项 u64/u32 权重表。
* `dat\Seabk.mrg`（25 条，每条 38400 字节，名字 `9801..`）、`SeaBK1.mrg`(空)、`dat\9857.sbk`(38400)：**是 mrg 容器 / 同尺寸块**，每块 38400 字节且绝大多数为 0，和 `.sbk` 同尺寸 —— 海面/航行地图的碰撞(可通行)格，38400 = 160x240 或 150x256 的 1 字节一格 [推测]。`dat\Scene6.mrg`（2 条，`006406/006407`）是普通 rle6 位图，`wjres.py` 可直接转。

## 附：converter 输出格式

`python wjres.py <file.mrg|目录> -o out [--variants N] [--page 4096] [--no-jpeg] [--dump-chunks]`

每个 mrg 输出到 `out\<mrg名>\`：
* `atlas_0.png …`：RGBA 图集（1px 间隔，默认单页 ≤4096²；超大图单独成 `atlas_bigN.png`）。
* `atlas_vK_0.png`：role 的第 K 套换色图集（`--variants`）。
* `jpg\*.jpg`、`wav\*.wav`、`chunks\*.bin`：原样/解压后的记录。
* `atlas.json`：
  ```json
  { "source":"boy05.mrg", "count":…, "palFile":"boy05.pal",
    "stats": {"cp":36},
    "images":[ {"name":"ROLE\\M1MA01.CP3","index":14,"kind":"cp","frame":5,
                "ox":-10,"oy":-44,"page":"atlas_0.png","x":0,"y":0,"w":17,"h":27},
               {"name":"1100","kind":"rle6","cw":12,"ch":18,"page":…,"x":…,"y":…,"w":96,"h":144} ],
    "files":[ {"name":…,"kind":"jpeg","file":"jpg/0007.jpg"}, … ],
    "variants": { "1": [ 同 images 的项, 但 page/x/y 指向 atlas_v1_N.png；只含在 .pal 里有块的记录 ], "2": [...] },
    "palettes": { "m5ma01": [[ "rrggbb"*256 ]*6 ] } }
  ```
  `ox,oy`（cp 才有）= 相对锚点偏移，画图时 `draw(x+ox, y+oy)`；`cw,ch`（rle6）= 精灵表单元格。
* 速度：纯 Python，实测 `role\boy05.mrg`(2.1MB, 36 条 cp, 约 2700 帧) 约 14 秒，即 ≈150KB/s；`role\npc*.mrg`(百 MB 级) 要十几分钟～一小时，可按需只转部分文件。
