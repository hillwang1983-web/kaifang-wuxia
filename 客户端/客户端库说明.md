# jyclient —— 逆向出来的客户端协议库

文件：`jyclient.py`（库）、`client_scenario.py`（场景测试）、`parse_0x1e.py`（0x1E 解析）、`packet_proxy.py`（编解码、抓包代理）。
只用标准库，asyncio。目标是以后做网页版：浏览器 <-WebSocket-> 网关（用本库）<-TCP-> 游戏服务端。

## 已实现的动作与状态

| 方法 | C2S | 说明 |
|---|---|---|
| `login(jyid)` | 0x01 | 返回握手帧；账号不存在 / 被拒时服务端静默断开，返回 None |
| `start()` | 0x19 | 收完登录序列（到 0xA9 为止） |
| `move(x1,y1,x2,y2)` | 0x06 | 尾部 3 字节未解，原版不校验 |
| `say(text)` | 0x02 01 | 公共聊天，自动转 BIG5 |
| `teleport(map,x,y)` | 0x5D | 原版不校验 |
| `equip(slot,item,state)` | 0x15 | 槽位 1 盔 2 项链 3 衣 4 披风 6 武器 7 护腕 8 戒指 9 鞋；背包没有的物品会触发全服「嘗試刷裝備」广播；槽位有装备时静默忽略 |
| `unequip(slot)` | 0x16 | 有效槽位一律回 0x18，空槽也回 |
| `use_item(item)` | 0x0B | 药品；背包没有 -> 「物品不足」；带 max精/神/内 的药原版不处理 |
| `shop_open(merchant)` | 0x09 | 商人 ID 见服务端 `data\商人.csv`；回商品列表（`client.shop`） |
| `buy([(item,n),..])` | 0x0A | 原版规则：「商品」列=1 才能买、单价恒为 1、每条只入包 1 件、有一条不合格整包拒绝 |
| `send(type, payload)` | 任意 | 自动加 `F6 11 <序号>`，密钥 = 基数 ^ 序号 |

状态：`me`（0x1E 解析结果，之后随 0x7B / 0x17 / 0x18 / 0x0B / 0x0A 更新：属性、装备、背包）、`pos`、`map_id`、`players`（同图玩家，0x02/0x61/0x62/0x05/0x06 维护）、
`chat_log`、`notices`（0x14 / 0x1A 文字）、`shop`、`names`、`rekeys`；`bag_count(item)`。动作方法只负责发送，回包靠 `drain()` / 监听器拿。
C2S 密钥基数 = `derive_key(最近一次收到的种子)`，握手种子和每个 `0x99 04 <种子>` 都会更新。

## 结果（2026-10-18）

- 登录握手 34 字节与原版逐字节相同；`0x19` 回 19 帧（+ 握手共 20），顺序与原版夹具相比，123456 多一条 `0x14 0e 本服贊助王…`（该号是赞助王，文档说明会触发）。
- 聊天：B 收到 `04 01 <jyid> 文本`，A 自己不收，A 收到两条 `0x7B`（饮食、饮水 −5）；下线通知文字是"离開游戲"（简繁混用，原样）。
- 传送：自己收 `08 02 6d 3d 31`，换图时再收新图上每人的 `02 + 82`；旧图的人收 `62`，新图的人收 `61`；同图后移动广播互相可见。
- 换密钥：种子 `0eaea533` → 基数 0xaa，客户端改用新基数后移动被处理；仍用旧基数 0x7d 时被静默忽略。
  注意这一项连的是新服务端，它和我用的是同一个公式，所以只证明客户端实现自洽；
  公式本身的外部证据是网金复刻在原版上验证过的种子 …31/33/36（见其 docs/药品效果.md）。

## 网页网关（2026-10-18）

`gateway.py` + `web/index.html`：浏览器 <-WebSocket/JSON-> 网关（每个浏览器连接一个 `JyClient`）<-TCP-> 游戏服务端。只用标准库，自带最小 HTTP 和 WebSocket。

```
python gateway.py                          # 页面 http://127.0.0.1:8088/ ，上游默认 127.0.0.1:6732（新服务端）
python gateway.py --server 127.0.0.1:6731  # 连原版服务端：它强制单点登录、会写库，谨慎
python test_gateway.py                     # 协议 / 安全自测（需要网关和上游服务端都在运行）
python test_gateway.py --port 8089 --mutate  # 再测脱 / 穿 / 开店（共 59 项）——会改角色数据，只在隔离服务端上用
python build_sprites.py --model 1          # 预生成身体 / 阴影 / 默认头发图集（其余层网关按需生成，约 2 秒）
python test_looks.py                       # 外观表离线自测 11 项（Item3.Dat + boy01.mrg）
python x86mini.py <exe> <起始VA> <结束VA>  # 极简 x86-32 反汇编，给 Ghidra 没反汇编的区域用（0x51cbac 外观表加载函数就是靠它读出来的）
python gateway.py --pic <share\pic>        # 地图背景目录，默认 ..\share\pic
```

页面：登录（只输账号 jyid，协议本身没有密码）、角色状态（精气神内条、七属性、金钱名声等、装备、背包带物品名、武功技能）、
公共聊天（收发、系统消息、上下线通知、自己的饱食饮水随聊天变化）、同图玩家、按坐标移动、"显示帧"调试开关。手机宽度单列。
浏览器消息：`login / say / move / teleport / equip / unequip / use / shop_open / buy / debug / logout`；
网关推送：`me / patch / pos / players / chat / notice / shop / frame / status / error / closed`（见 gateway.py 文件头）。
页面入口：装备行「脱下」；背包行「使用」（药品）、槽位下拉 +「穿」（装备，下拉默认按物品编号前缀推测，服务端不校验类型）；传送表单；商店折叠区（商人下拉 + 商品列表 + 数量 + 购买，不可买的灰显）。
网关层先拦：穿背包里没有的物品（否则会触发全服刷装备广播）、无效槽位、数量不在 1..9999、购买列表超 20 条、坐标 / 地图越界。
装备 / 背包 / 属性变化后网关合并 0.15 秒内的更新，重发一次完整的 `me`。

**地图画面**：页面右上是一块 canvas。背景图是原版 `share\pic\SceneBG*.mrg` 里**以地图编号命名的记录**——整张 JPEG（`资源格式说明.md` §2.1，不需要转换）：
2801 号 4800×3900、8105 号 2200×1200、2200 号 1000×750，共 635 张。**角色坐标就是这张图上的像素坐标**（2801 里角色在 (4242,1742)，8105 里 (1151,499)，都落在图内）。
网关启动时只读各个 .mrg 的记录表和名字表建索引，`/maps/<编号>.jpg` 按需从原文件里切出一张返回，不复制、不转换、只读。
页面（2026-10-18 重做为全屏地图 + 浮层 HUD）：整个窗口是地图，人物精灵带名字和聊天气泡；滚轮缩放；左上角色小面板（精气神内、坐标、金钱）、顶栏页签（角色 / 背包 / 技能 / 商店 / 传送 / 设置）、左下聊天、右下小地图（点它也能走）。**点击地图 = 自动寻路走过去**（见下面「地图碰撞与寻路」）；传送换图后自动换背景。

**人物精灵**（替换圆点）：`build_sprites.py` 用 `wjres.py` 的解码函数，从 `share\role\boy01.mrg` 按需生成"层 × 调色板套"的小图集（只含站立 CP7 和行走 CP1 × 8 个方向），
网关第一次被请求 `/sprites/<模型>/<层>_<套>.json|png` 时生成并缓存在 `web\sprites\<模型>\`（每层约 0.5 秒、100~300KB；`python build_sprites.py --model 1` 可预生成身体 / 阴影 / 默认头发）。
网页端 `web\sprites.js`：8 方向（位移 -> 方向用 loginp.exe 0x767994 的算法）、站立 150ms / 行走 100ms 一帧、位置补间（行走速度 200px/s 是**自拟值**，原版逐点路径走，速度没追）、镜头跟随补间中的位置。
画点 = 脚下 (x, y-56) + 帧的 (ox, oy)；缩到 0.35 倍以下（全图视图）退回圆点。

**外观是怎么定的（loginp.exe 逆向，2026-10-18）**——网关 `gateway.Looks`，`test_looks.py` 11 项自测：
- 装备外观表在内存 `this+0x281058`，每个 ID（16 位）14 字节 = 两个 Delphi shortstring[6]（前一个**女**、后一个**男**）。**0x51cbac**（Ghidra 没把这一段识别成函数，我用 `x86mini.py` 手工反汇编）
  从 `dat\item3.dat` 读入：文件 320 字节头 + 每条 299 字节，ID = 记录首 u16，女外观码在记录 `+0x38`，男外观码在 `+0xaf`；表里 `0xFFFF` 的两个串被写成常量 `"ma0101"`（默认头发）。全客户端只有这一处写表（对 `58 10 28 00` / `5f 10 28 00` 两个偏移量做了全文件字节搜索）。
- 外观码 6 个字符，如 `ma0101` = 层名后 4 位 `MA01` + **调色板套号 `01`**：解析函数 `0x521be4` 取前 4 位、后 2 位转整数；绘制函数 `0x5253c8` 里调色板地址 = 基址 + 套号×0x200（256 色 × 2 字节），对应 `.pal` 里每层 6 套颜色。
  层名 = 模型前缀（boy01 是 `M1`）+ 前 4 位大写，例如 `M1MA01`。
- 男模型（1..9、0x14..0x19）取男码，其余取女码，选中的为空就用另一个，都空 = 这个槽不画（0x521be4 开头的 switch）。
- 玩家对象 `+0x134 / +0x139 / +0x13e` 三个 16 位值（头 / 衣 / 武器，也就是 0x02、0x61 包里的三个 LE16 物品 ID）传给绘制函数：头槽为 0 时改成 `0xFFFF`（于是画默认头发 `ma0101`），衣 / 武器槽为 0 不画；
  叠放顺序（0x5252f8）：阴影 → 身体 → 槽，模型 3..9 的槽顺序是 衣、头、武器，其余是 头、衣、武器。某个层在该模型的 mrg 里不存在（如 `WF01` 只有 6 号以上模型有）就不画。
- 代码字母：武器 `wa..we`（刀 / 棍 / 枪 / 剑 / 鞭，渲染对过）、头 `ma/mb/mc`、`pa..pd` 在 18xxx、19xxx 号物品（名字带「爪」）上、`wf` 在 26xxx 靴子和 27xxx 衣服上——字母和物品类别的对应是原版数据决定的，我们只照抄机制，不再按名字猜。

**直接后果（重要）**：`Item3.Dat` 里有外观码的物品只有约 4947 条（共约 2 万条记录），而且**不包含服务端自己的 GM 装备**（25091 神威麒麟盔、27181 战甲、12498 星剑等），
`Item4.Dat` 里也没有这些 ID 的记录，客户端也没有别处写这张表。所以按原版客户端的逻辑，123456 这个号只会画出阴影 + 身体（**连头发都没有**：头槽里有非 0 的物品 ID 就不会用默认头发）。
这是照代码得出的结论，**没有拿原版客户端运行验证**（不能运行）；如果和真实画面不符，最可能的原因是 Item3.Dat 之外还有我没找到的来源。
服务端的武器编号 11xxx–15xxx 与客户端 Item3.Dat 里的武器编号 2xxx–7xxx 是两套，**本地资料里没有转换表**（查证过程和证据见 逆向笔记_loginp.md 末尾「服务端武器编号 -> 客户端外观表」：五个 Item*.dat 都没有这些编号、加载函数只有一处、编号不经转换、服务端没有外观列）。推断是客户端有自动更新，随包的 dat 是旧版；要还原需要更新后的 Item*.dat。
- **外观兜底开关（非原版行为，默认关闭）**：`python gateway.py --look-fallback`——Item3.Dat 里没有的**武器**，按 `装备数据.csv` 的 itemtype2 画对应层（20 刀 -> WA、22 棍 -> WB、25 枪 -> WC、23 剑 -> WD、24 鞭 -> WE，款式 01、调色板第 0 套；爪 29 没有对应层，不画）。只管武器，头盔 / 衣服不兜底（它们的层和模型有关，见上）。表里有的武器仍然按表。页面日志会提示"外观兜底已开启"，`look.info` 里兜底的条目带 `fallback: true`。类型 -> 层的对应是在渲染图里肉眼对过的，但**原版客户端没有这个机制**。`test_looks.py` 17 项、`test_gateway.py --fallback` 57 项覆盖。
- **模型**：现在所有人都用模型 1（boy01，男）。`renwu.sex`、`head_image`、`mode` 在三个测试号上全是 1，没有变化样本，没法验证哪个字段决定模型；
  女性 / 其它模型的外观码取法已按代码实现（`Looks.layers(model, ids)`），页面还没按字段选模型。
- 别人的外观来自 0x02 / 0x61 里的三个 LE16（`jyclient` 记在 `players[jyid]["look"]`），同样走上面的规则。
- 测试用：`client_actions_test.py` / `isolated_server.py` 的临时库里把 1234567 穿成表里有码的装备（头 16640 `mb0105`、衣 18708 `pb0101`、武器 2978 `wd0102`），网页里能看到头盔（5 套）、橙色铠甲（1 套）、剑（2 套）。

**地图碰撞与寻路**（`WalkIndex`，网关 `/walk/<地图>.json`）：每张图的碰撞位图在 `dat\WSG*.dat`（.mrg 容器，记录以地图编号命名，1232 个记录名、650 张图的记录通过格式校验）里：
记录 = Pascal 地图名 … 偏移 51 起 u16 宽、高（像素）、行数、列数，偏移 59 起位图；格子 20×20 像素，行数 = ceil(高/20)，列数 = ceil(宽/20)，**每行 列数//8 + 1 字节**，低位在前，1 = 不能走。
验证：8105 / 2200 叠在背景上街道和楼梯是空的、房子是满的（逐像素看过）；2801 必须按"每行 31 字节"才对齐（MAP.csv 里 79 个到达点 74 个落在可走格，按 30 字节切只有 46%）。
同一张图可能出现在多个 WSG 文件里（104 张，内容略有不同，是版本更新），网关按文件号从小到大后者覆盖前者。

**前景物件与遮挡**（2026-10-18）：碰撞位图后面是这张图的前景物件列表，每条 = `u16 50` + Pascal 名（51 字节，如 `280135`）+ `u16` 宽、高、x、y + 3 个 `u16` + `u8` 足迹列数、行数 + 足迹（列数×行数 字节 0/1，每格 20 像素，覆盖物件图）。
物件图在 `pic\Scene*.mrg` / `ScenePic.mrg` 里同名的 rle6 记录（尺寸等于 宽×高；同名图在多个文件里时按尺寸选）。**(x, y) 是物件图在背景上的左上角**——把物件图叠到背景同一位置，像素差平均只有 ~7（RGB565 / JPEG 的量化误差），偏 1 像素就升到 ~28，偏 5 像素 ~45，所以是精确对位的抠图。
足迹最底下一行 1 在图像最底一行（148 个里 137 个），所以深度线取 `y + h`（图像底边）。不同地图的列表头不一样（8105 是 `u32 0 + u32 个数`，2801 是 `u16 2 + u16 69 + u32 个数`），个别图里夹着别的记录类型（`u16` 不是 50），
所以网关不顺着列表走，而是按"`u16 50` + 数字名"的特征逐条找、再用尺寸一致性（足迹列数 = ceil(宽/20)、行数 = ceil(高/20)）过滤：2801 号图找到 155 条，全图 8637 条、4231 种不同的图，其中 105 张在 Scene*.mrg 里找不到同尺寸的。
网关 `/objects/<地图>.json` 给列表（`{n,x,y,w,h,d,u}`），`/obj/<名>_<宽>x<高>.png` 给贴图（缓存在 `web\objects\`，没有就用 `build_objects.py` 现生成，需要 Pillow 和客户端 `pic\Scene*.mrg`；`python build_objects.py --all` 预生成全部，约 2 分钟、3353 张、115MB）。
页面用画家算法：人物按脚下 y、物件按 `d` 一起排序，**只有"有人走在它后面"（脚比底边靠上、人物矩形与物件重叠）的物件才重画**盖住人，名字和气泡最后画所以还能看见。验证：站到 2801 号图中华镖局的屋顶后面，人物被整个遮住，只剩名字。
页面寻路：A*（8 方向，斜着走要求两侧都空）→ 视线检查拉直 → 路点序列，走到一个点才向服务端发下一段 0x06（原版也是边走边报位置）；目标点在阻挡格上就走到最近的可走格；没有碰撞数据的地图直接走直线。
网关也会拦：`move` 如果穿过阻挡格返回"这条路被地形挡住了"（起点站在阻挡格上——传送 / 登录落点——时只要求落脚点能走）。设置页的"显示碰撞格"能看到红色的挡路区域。

**NPC 摆放**（2026-10-18，`npcdata.py` 的 `NpcIndex`，网关 `/npcs/<地图>.json`）：`pic\NpcMrg*.Mrg`（NpcMrg / 2 / 3 / 4 / 5，.mrg 容器，记录名 = 地图编号，共 3433 个，1300 张图有 NPC 条目、合计 8301 条；同一张图在多个文件里取文件号最大的）。
记录是 LZSS 压缩（magic `56 8D 0F 20` + u32 解压长度），解开后每个 NPC 条目：`01 + u32 n + n×u32 事件号` + `u16 编号 + u32 x + u32 y（单位：20 像素格）+ u8 朝向 + u16 型号 + Pascal 名（BIG5）` + 零填充 + `u16 编号（重复一次）+ 02 + 8×FF` + 后续字段（未解）。
条目之间没有长度字段，所以按"名字后面重复出现 编号 + 02 + FF×8"找。**型号 = 服务端 `MOB数据.csv` 的 mob_id**（38xxx / 39xxx / 41xxx 是 NPC 和场景物件，≥ 50000 是怪物；39015 肉商、41025 打铁炉 的名字与 MOB数据.csv 一致）。
网关返回 `{id,name,x,y,dir,model,kind,ev}`：x y 取格中心像素（`格×20+10`），kind = model ≥ 50000 为 `mob` 否则 `npc`，ev = 事件号个数。2801 号图 300 条（其中大量是怪物刷新点，名字像"小隊長7"）。

**NPC 对话与事件脚本**（2026-10-19，`evtdata.py` + `evtengine.py`，网关 op `talk` / `dlg` / `dlg_close`，事件 `dialog`）：
数据在 `pic\EvtMrg*.Mrg`（事件脚本，记录名 = 地图编号，小编号补零成 4 位如 `0014`，LZSS 压缩）和 `pic\TextMrg*.mrg`（对话文本，16 万条）。格式是从 loginp.exe 的加载器 `FUN_0091d410` 逐字节抄的（rea / Ghidra 反编译），3433 条记录全部能按它读完。
- **事件记录**三张表：节点表 `u32 N1` + N1 个节点 `[名字 20 字节(Pascal，尾部有垃圾) + u8 t(1 主事件 / 0 副事件) + u32 nA + nA×u32 条件号 + u32 nM + nM×u32 动作号]`；条件表 `u32 N2` + 每项 `u8 类型 + 载荷`；动作表 `u32 N3` + 每项 `u8 种类 + 载荷`（载荷按种类不同，见 `evtdata._cond / _act`）。记录末尾可能有多余字节（编辑器改短记录没截断留下的旧内容，原版加载器读完三张表就停，这里一样）。2 张图（1319、2102）里有几种没解的动作种类，解析中途跑偏。
- **事件号 = 节点的 0 起序号 = 服务端 `0x6B` 的事件 id**。验证：服务端 `事件.csv` 里 7252 个有结果的事件，4500 个的标记 / 物品 id 恰好等于同序号节点的"效果"动作里的 id（其余多是客户端数据比服务端旧或只部分重合）；NPC 的事件号列表指同一套序号（朱一章的 9 个事件全是群英会相关的名字）。
- **条件**：type1 = 标记 / 物品都有（数量 ≥ n）且属性 ≥；type2 = 这些标记 / 物品都没有（属性不满足）；type3 = 属性 ==；type4 = 属性 !=（门派 65：丐帮大会节点要 `==26`，"门派"节点要 `!=0`）。属性号 = 服务端 `0x7B` 子类型的十进制（61 名声 `0x3d`、43 实战、68 历练、65 门派、24 当前血…）。type 0xb–0xe 等没见到数据的类型按"成立"处理。**这些语义是用数据对出来的，没有逐条对反编译的求值函数**，所以少数条件可能和原版不同。
- **动作**（已验证 / 对出来的）：1 文本（文本号列表，`-1` 分隔；`-1` 开头 = NPC 先说，否则玩家先说，轮流）；28 `[(说话者 NPC 型号, 文本号)]`（0 = 玩家）；14 提示文字（"獲得 金錢…"）；5 效果（标记 / 物品 / 属性变化，服务端执行，这里发 `0x6B 事件号`）；9 选单 `[提示文本, (选项文本, 目标节点)…]`；16 随机挑一个子事件；11 转到节点；10 **打开商店（商人 id = 服务端 商人.csv）**；2 战斗（未做）；3 / 27 动画 / 时间（忽略）；19 彩票 / 拉霸、26 分支等没解，显示"未實作的動作 N"。
- **点 NPC 的流程**：按 NPC 的事件号列表顺序，第一个"主事件且条件都满足"的节点执行；网关把对话一步一步推给页面（`say` 一页话、`menu` 选单；效果事件在中途直接发给服务端，服务端回的 `0x77` / `0x6B` / `0x7B` 折进本地状态，页面的背包 / 属性随之刷新）；`shop` 动作结束对话并发 `0x08` 开店。页面：点 NPC → 走到旁边自动开口 → 底部对话框（点击 / 回车 / 空格继续，选单点选项或数字键，Esc 离开）。
- **文本库** `TextMrg*.mrg`：一条记录 `TEXT`：`u32 解压长度 + u32 压缩长度 + u32 条目数 N`，N×10 字节索引 `(u32 id, u16 长度, u32 偏移)`，然后 gzip 压缩的文本区；每条按 `FUN_0092213c` 解密（偶数长度：前半段奇数位与对应后半段位互换并 XOR 0x6B；奇数长度：奇数位取镜像位 XOR 0x6B），内容是 BIG5。同一个编号在几个文件里是不同版本：TextMrg2 是简体字版，TextMrg / 3 / 4 是繁体字版（原版先查 TextMrg2）；网页版优先繁体。
- **协议**：`jyclient.event(事件号)` 发 `0x6B`：`[4 字节 X][地图 LE16][事件 id LE16]`（地图必须是当前所在地图，否则服务端按"刷事件"处理）；`client_actions_test.py` 对隔离服务端测了事件 53（得到物品 / 标记 / 名声 / 历练）和事件 32（缺标记）：回包 `77 14 77 14 7b 14 7b 14 7d`，本地状态跟着变。
