# 交接：战斗命令栏的两个 C2S（给服务端会话）

客户端侧（jyclient / 网关 / 网页）已经实现了战斗命令栏的 **防 / 闪 / 休 / 逃**，需要服务端补两个 C2S 指令。**以下全部来自对 `loginp.exe` 的静态逆向，没有对原版服务端抓包验证过**（本机抓不了包）。凡是写了【确】的是从客户端代码直接读出来的；写了【推】的是我的推测，请你按原版行为或你自己的判断处理。

## 1. 命令号

命令号 = 客户端命令表的下标（全局串表 `0xa12310`，36 项）。它同时是实体"当前动作"字节、也是 C2S `0xD7` 第 5 字节（cmd）的取值空间。【确】

| 号 | 命令 | 号 | 命令 |
|---|---|---|---|
| 1 | 移動(W) | 7 | **防禦(G)** |
| 2 | 一般攻擊(A) | 8 | **閃躲** |
| 3 | 特殊攻擊(S) | 9 | **養精蓄銳(R)** |
| 4 | 暗器(T) | 10 | **逃跑(E)** |
| 5 | 毒術(P) | 11 | **自動** |
| 6 | 醫療(M) | 12 | 裝備（只开窗口，不发包） |

## 2. C2S `0xDE`：防禦 7 / 閃躲 8 / 養精蓄銳 9 / 自動 11

载荷 **10 字节**【确】（`FUN_009b6874` 的 0xDE 分支，`0x9ba31b` 起）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | 自己的 jyid，LE32 |
| 4 | 1 | 命令号：7 / 8 / 9 / 11 |
| 5 | 4 | 计数器，LE32：`时钟 − 20×随机 − 50×G[0x1346a8] − (FUN_009b6380() & 0xff)`，和 `D7` 里那个"攻击间隔"计数器是同一个东西 |
| 9 | 1 | 校验字节：`(时钟 + 0x53e − 命令号) % [0xa26304] + 1` |

- 客户端发送前会先把命令号写进 `G+0x25e`，发完调 `FUN_0099e2c8(1)`。
- 计数器和校验字节我们的客户端发的是"毫秒时钟 / 0"，**不要校验它们**（新服务端本来就不校验 D7 的同类字段）。
- 客户端发 `0xDE` 之前的本地条件【确】：
  - 養精蓄銳(9)：战斗模式 0xb / 0xd / 0xf 直接发；其它模式要自己的精 / 神比例满足条件，否则只在本地提示「精或神不足無法休息」、不发包。
  - 自動(11)：另外置 `G+0x24d6270 = 1`，本地提示「自動功能開啟」。
  - 防禦、閃躲：没有额外本地条件。

### 期望回包【推】
原版怎么回 `0xDE` 我**没见过**。最小可用的做法：当作"出招转发"，回 **S2C `0xD7`**（载荷 = 前 16 字节，和你现在转发 C2S `0xD7` 同形）：

```
id(LE32) = 发令者的 jyid | cmd(1) = 命令号 7/8/9/11 | b5(1) | skill(LE32) = 0 | b10 | col | row | tcol | trow | dir
```

客户端收到 `D7` 会把 cmd 写进该实体的当前动作字节、写技能 / 两个格坐标 / 朝向并播放动画；网页端对 cmd 7/8/9/11 只记一行日志，不冲向目标、不放刀光，所以回包里的坐标和技能填 0 / 发令者所在格即可。

### 命令的游戏效果【未知】
防禦（减伤？）、閃躲（提闪避？）、養精蓄銳（回精 / 神 / 气？）、自動（让服务端代打？）各自在服务端侧该产生什么效果，**客户端代码里看不出来**。客户端只负责发；伤害公式、回复量是服务端的事。建议先做"只回 D7 转发、不改任何数值"，等有原版行为依据再补。

## 3. C2S `0xF9`：逃跑（命令号 10）

载荷 **空**【确】（`FUN_009cb16c(sock, 0xF9, 0)`）。

客户端发送前的本地条件【确】：
- 劫镖类战斗不许逃（提示「你太遜了吧,有沒有搞錯呀,劫鏢者還想逃亡,休想!」）；
- 站在"逃離點"上才发：当前格满足 `FUN_009b423c` / `FUN_009b4cdc(列, 行, 模式, 2)`，或格表标记 `+0x139a09 == 1`，或持特定物；否则本地提示「此處非逃離點」、不发包。

**我们的网页端没有"逃離點"的格标记数据，所以会直接发 `0xF9`**，是否允许逃跑完全由服务端决定。

### 期望回包【推】
- **允许逃跑**：按"战斗结束"处理，和 `C2S 0xE5` 的收尾一致：`S2C 0x81`（`01` = 我方存活）、`0x82`、**`0xE6`（自己的 jyid）**、`0x7B 18`（气血）。客户端收到自己的 `E6` 才复位战斗状态（见 `战斗协议_客户端侧.md` §3）。
- **不允许**：什么都不回即可（网页端只显示"已请求逃跑，成败由服务端决定"，战斗继续）；也可以回一条提示类消息，原版有没有这条回包不知道。
- 逃跑成功时敌方是否继续存在、是否有死亡惩罚、掉落如何结算，原版行为不知道。

1. `0xDE`：采用「回 D7 转发」。已进场且活着时回 S2C `D7` = jyid + 命令号 + 11 个零；命令号只认 7/8/9/11，别的静默。数值效果**没有**（防御 / 闪躲 / 回气都不改数值）。原版没有正确校验字节一律静默，没法对照。

3. 逃跑成功后的死亡惩罚 / 掉落：没有特殊处理（按 E5 的普通结束）。
4. `opcodes.py` 已登记 C2S `0xDE`（partial）、`0xF9`（verified）和 S2C `0xD7`、`0xF9`。详见 `C:\游戏\网金复刻\docs\战斗.md`。

## 9. 游戏时钟（2026-10-20，客户端会话，静态逆向 loginp.exe，请服务端会话看一眼）
- **S2C 0x33 的第一个 LE32（心跳计数）和 S2C 0x1E 开头的 LE32（header counter）就是游戏时钟 T**，一格 = 一次心跳（约 75.6 秒，客户端按 75 秒折算）。证据：0x33 的处理块 0x626b2c 读两个 LE32，第一个交给 0x6bdc48 存成时钟，第二个（在线时间）存到玩家 +0x770；0x1E 的处理块 0x6263e4 把开头 LE32 交给 0x6bdc08，先取整到 4 的倍数、余数 ×75 秒记为已过时间。
- 日历（0x6bdad8 / 0x8d66bc）：年 = T // 34560，月 = T % 34560 // 2880（0 起），日 = T % 2880 // 96（0 起），时辰 = T % 96 >> 3（0..11），刻 = T & 7；一天 96 格（约 2 小时现实时间），一月 30 天，一年 12 月。
- 用处：事件条件 6（381 条 / 461 个节点）按这个日历判，例如「初一開放入寺」（每月 1 日全天）、「十五開放入寺」、各种按时辰出现的 NPC / 怪。客户端已按这个实现（`evtengine` 条件 6，`jyclient.game_time()`）。
- 请确认：新服务端 0x1E 里的 header counter 目前像是常量（我这边测到 1），而 0x33 的计数从启动起递增；如果想让这些日期 / 时辰条件生效，两处应给同一个**随时间递增的计数**（0x1E 登录时给当前心跳计数，之后 0x33 递增）。原版 0x33 帧「第一个数在变」就是它。

- **第 9 节的原版实测（2026-10-20，客户端会话，对原版 127.0.0.1:6731，测试号 8617293）**：登录时 0x1E 开头计数 = 3746，之后 0x33 第一个数每约 75 秒 +1（登录后第 55 秒收到 3747，第 130 秒收到 3748，相隔 75 秒）；再登录一次拿到的 0x1E 开头计数 = 3748，和最近一次心跳一致。也就是说原版 0x1E 开头计数 = 当前心跳计数，随时间递增，上面的推断成立。新服务端要让日期 / 时辰条件生效，就按这个给。
