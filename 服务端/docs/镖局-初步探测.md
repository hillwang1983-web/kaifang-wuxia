# 镖局（3D / 3E / 3F / 40 / 41）：初步探测，没做

结论先说：**没有实现**。这一组指令的反编译很乱、原版自己的数据表又缺，摸到的行为不能自洽，继续下去没有可靠的对照目标。记在这里免得重复劳动。

## 代码位置

- `0x8c05dd`（盘点里记的 `3F`）其实是一个函数里顺序比较 T[3] 的三个分支：`3E`（列表）、`3D`（托镖）、`3F`（取镖，回 `F5 B3 6A 02 4B` 长帧）。2400 行，里面塞满「镖局.程序命令标记：{n}」调试串（没有行为）。
- `0x8c752d`（`41`，押镖 / 交镖）约 1500 行，文字：「未到交鏢時間！」「押鏢刷錢！武功隨机降一級！」「押鏢成功！」，日志 `押镖.txt`。
- 数据：内存数组 `DAT_00dd87e4`（每个玩家一条：jyid、两个子数组）和 `DAT_00dd87e8`（带锁），启动时应从 MySQL `biaoju` 表读，**这份库里 `biaoju` 只有 .frm，读不了**，所以原版里是空的。

## 实测到的（8617293=A 向 1234567=W）

- `3D` 托镖载荷：`N(1)` + 收件人名字 N 字节（BIG5）+ 标记(1) + 物品 ID(LE32) + 1 字节(未解) + 数量(1)。至少 `N+9` 个 token。
  检查（从反编译）：收件人不存在 → `1A 12`；物品表里「可托镖」标志为 0 → 「此物品不能托镖」；收件人镖局总数 + 数量 > 200 → 「对方镖局總數不得超過200！」；自己背包数量不够 → 「物品數量不足，請重登﹗」；成功 → 收件人收到「<名字>　托鏢給你」，自己收 `1A 0E` 物品提示，并写 `镖局记录.txt`。
- 实测发了一条形状正确的 `3D`：A 收到「物品不足」+ `1A 0E 00 00 46 e3 00 c8`，W 收到「123456　鏢給你」，但**下线后库里两边的背包都没变**，之后 `3E`（列表）两边都回 `1A 10`（空），`3F` 无回应——和反编译读出来的流程对不上（疑似「物品不足」才是真结果，托镖通知先发了）。
- `3E` 任意载荷：没有记录回 `1A 10`；`40` 任意载荷回 `4D 04 88 13 00 00`；`41` 任意载荷回全服公告「<名字>押鏢刷錢﹗武功隨机降一級﹗」（没有进行中的押镖就当刷钱）。

## 为什么停

要做对，需要先弄清 `biaoju` 记录在内存里的结构、`FUN_008c5588` / `FUN_008c4d59` 等辅助函数、以及真客户端怎么走（托镖 → 等时间 → 交镖拿钱）。没有真客户端的流量，只对着缺数据表的原版摸，投入大、结果难验证。建议等真客户端能连上新服务端、有抓包之后再做。
