# 商店：开店 C2S 0x09、购买 C2S 0x0A

方法：`tools/shop_probe.py` 对原版发包、读 MySQL；反编译 `0x5ff37d`（"购买物品"，同一个函数处理 0x09 和 0x0A）。
新服务端（`jyserver/shop.py`）对同一套 9 个包（开店 ×3、批量买、0 件买、不能买的、商人表里有但不能买的、钱不够、混合批量）
输出逐行相同；`tests/test_shop.py` 的期望值全部来自原版回包。

## 开店 C2S 0x09

载荷 = 商人 ID（LE16，对应 `data/商人.csv` 的 ID 列，如 53 = 京城药店）。

- 认识的商人：依次回
  1. `0x1A`：`64` +「批量購買，需重登后顯示﹗」
  2. `0x09`（长帧）= `00` + 每件商品 `[物品ID LE32][商人表里的数 LE32]`（那个数在商人表里写的是 1000/5000…，客户端怎么用不清楚，原样发）
  3. `0x1B`（长帧）`1f 79 00 00 32 02 00 00 00`
  4. `0x1B`（长帧）`c9 af 00 00 3c 0c 00 00 00`（后两条是常量，内容含义未知）
- 不认识的：`0x1A`：`64` +「此商人沒錄入，通知GM﹗」+ 商人 ID 的十进制 ASCII，再一个**空的** `0x1B`（短帧）。

## 购买 C2S 0x0A

载荷 = 若干条 8 字节记录 `[物品ID LE32][数量 LE32]`（批量购买）。

**原版的规则（有几条很反直觉，新服务端照做）：**

- **不看开没开过店、不看这家店卖不卖这件**：只要物品在 `装备数据.csv` 的「商品」列 = 1 就能买。商人表里写着卖、但「商品」列是 0 的
  （如咖哩粉 44107）一样被拒；神威麒麟盔 25091 也被拒。只要一条记录不合格，整个包都不处理，回 `0x1A`「有不允許購買商品，該行為已經記錄﹗」，
  并在 `jilu\日期.txt` 记 `<jyid>刷购买：<物品ID>`。
- **单价恒为 1**：按「数量」扣金钱 `jy_money`，不管商人表（1000/5000…）和物品表（价格 10000…）里写多少（实测 12 种物品）。
- **背包只加 1 件**：不管记录里的数量是多少（包括 0）。已有同种物品（`state=200` 的那行）就 `shuliang + 1`，否则新增一行。
  商店界面上的提示「批量购买，需重登后显示」说的就是这个。新服务端默认照做，开关是 `shop.FAITHFUL_SINGLE_UNIT`；
  改成 `False` 就按数量加。
- 数量 0 也算买成功：不扣钱、照加 1 件。
- 钱不够（总价 > 金钱）：整包不处理，回 `0x1A`「錢不夠﹗」+ 空的 `0x1B`（短帧）。
- 代码里还有背包上限 499 件（"身上总数超过499"），新服务端按同样的文字回 `0x1A`；**这条没有实测**（需要把背包塞到 499 件），文字和回包是按字符串推的。

**成功时的回包**（顺序固定）：

| 帧 | 载荷 |
|---|---|
| `0x7B`（长帧） | `3c 01 <购买后的金钱 LE32>`（子类型 0x3C = 金钱） |
| `0x0A`（长帧） | 每条记录 `01 <物品ID LE32> <这条之后的金钱 LE32>`（逐条的余额） |
| `0x1B`（长帧） | 每条记录 `<物品ID 低 3 字节> <耐久字节> 00 00 00 00`（8 字节；耐久取物品表，同背包记录） |
| `0x1A` | `64` +「購買成功﹗」 |

金钱和背包在**下线时**落库（和原版其它数据一样）。
