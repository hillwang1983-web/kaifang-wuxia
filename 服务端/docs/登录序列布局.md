# 登录序列布局（C2S 0x19 之后的 S2C 序列）

证据全部是**实测**：克隆测试角色（jyid 9999001）→ 改一个数据库列 → 登录原版服务端 → 对比回包差异
（`tools/layout_probe.py`），再用四个快照夹具逐字节验证（`tools/verify_state.py`、`tests/test_state.py`）。
实现在 `jyserver/state.py`。

## 0x1E 载荷

```
[0:4]    计数器（LE32；不是校验和。原版实测约每 76 秒 +1，起点不明，见 docs/新建角色.md「未解」；新服务端发运行分钟数）
[4:6]    背包记录条数 N（LE16，含末尾 (0,0) 结束记录）
[6:6+5N] 背包记录：物品ID(LE32) + 耐久(1)；按数量展开；耐久取自 装备数据.csv 第 10 列 / 药品.csv 第 3 列
[尾部]   固定布局；下表偏移以 N=23 为基准，实际偏移 += 5·(N−23)
```

尾部字段（`RENWU_FIELDS` 等表见 `state.py`）：

- jyid LE32 @166；名字 @170 和称号 `"V7Z0-"+昵称` @187，均为「长度前缀 + 内容」，字段宽 17
- renwu 整数列：map/x/y @204/208/212，精气血神内力、六维、zigong、经验、金钱、声望、生日、性别、门派等（见 `RENWU_FIELDS`）
- **武器强度 @274 / 防具强度 @276 不是数据库列**（库里恒为 0），而是身上 8 件装备的「攻击 / 防御」之和（装备数据.csv 第 8 / 9 列）；测试号 123456 实测 1610 / 8890
- 装备栏 5 字节记录（ID LE32 + 状态）@121 起：头盔、项链、衣服、披风、武器、武器（重复一次）、护腕、戒指、鞋
- 17 类武学 6 字节记录（等级 LE16 + 经验 LE32）@425 起
- char_equip 15 个 LE16 @395 起
- kf：条数 @528，记录 @529 起步长 11（+1 等级、+3 经验 LE24、+7 武功 ID LE16），最多 13 条
- 生活技能 11 项 5 字节（等级 + 经验 LE32）@673 起；`lirenexp` 不下发
- head_image @728，mode @729

## 文字编码

线路上是 BIG5 繁体，库里是 GBK 简体。实测规则：**BIG5 里本来就有的字原样发**（游 → `b4 e5`，不变成遊），
BIG5 里没有的简体字才转成繁体（戏 → 戲 `c0 b8`）。（**已更正**：现在的做法是先过 Windows NLS 简繁表再编码，
见下，游 不在表里所以不变；旧说法「BIG5 里有的字不转」对 万/云 之类不一定成立。）简繁表由 `tools/build_s2t_nls.py` 生成；旧版从 `MOB数据.csv`
（BIG5_NAME / GBK_NAME 两列逐字对齐）学出 531 个字，存 `data/s2t.json`。

## 未解

- 简繁表现在是 Windows NLS 的 2191 个字（项炼、钢剑等装备名与线上字节逐字节一致），MOB 表 94% 吻合；
  剩下的差异是人工校对的词义用字（岳→嶽、云→雲、志→誌…），原版对运行时文本是不是用 NLS 只有间接证据
- 「赞助王」条件推断为总消费点数全服第一，只有一个样本
- 0x1E 头部（背包记录之前的 6 字节）之外，N 变化时尾部是否还有依赖背包的字段：只测过 N=23 的模板 + 3 个不同背包的角色，都一致
- 背包物品由服务端启动时载入内存，运行中改物品表不会反映到包里（原版行为）
- 0x1E 开头的计数器：原版约每 76 秒 +1，起点不明（不是运行分钟数，也不是开机时间）；新服务端从 0 起每分钟 +1，客户端是否使用这个值未知
- 武器 / 防具强度对装备耐久、装备状态是否有影响：只验证了状态均为 50 的样本
