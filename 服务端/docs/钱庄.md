# 钱庄（随身钱庄）：C2S 0x23 / 0x22 / 0x71

方法：用 8617293 号对原版发包、读 MySQL `qianzhuang` 表；反编译 `0x891670`（调试名"钱庄"，分发函数把 `0x22` `0x23` `0x71` 三个 opcode 都交给它）。
新服务端（`jyserver/bank.py`）对 11 步序列（打开、存、取、取超量、存超量、取不存在的、数量 0、物品信息…）输出逐行相同；
`tests/test_bank.py` 的期望值全部来自原版回包。

## 库表

`qianzhuang(id, jyid, wupin 物品ID, shuliang 数量)`。每个账号有一行 `wupin=0, shuliang=0`（历史遗留，打开钱庄时放在清单最前面
4 字节）；其余每种物品一行。存 / 取是**搬数量**：背包扣、钱庄加（反之亦然），数量用光整行删掉；落库发生在下线时。
新服务端的角色库里对应 `rows['qianzhuang']`（`importer` 按 id 升序导入）。

## 打开 C2S 0x23（无载荷）

回 `0x28`（长帧）= `wupin=0 行的数 LE32` + 每种物品 `[物品ID LE32][耐久 1][数量 LE16]`，**最新存入的排最前**（按 id 降序）。

## 存取 C2S 0x22：`子类型(1) 物品ID(LE32) 耐久(1) 数量(LE16)`

耐久字节被忽略（回包里的耐久取物品表）。子类型 `00` = 存，`01` = 取。**物品 ID 为 0（想存钱）一律当"不够"**——钱庄只管物品。

| 情况 | 回包 |
|---|---|
| 存成功（含数量 0） | `0x0B` `8f bb 00 00 c8 01`、`0x77` `8f bb 00 00 c8 01`（两条都是固定内容，物品 48015 = 随身钱庄）、`0x27`（短）= `00 物品ID 数量(LE16) 当前金钱(LE32) 耐久` |
| 存失败（背包里不够） | `0x1A`：`64` +「物品數量不足，請重登﹗」，`0x77` 固定帧 |
| 取成功（含数量 0） | `0x0B`、`0x77`（同上固定内容）、`0x27`（短）= `01 物品ID 数量(LE16) ee dc 00 00`（末 4 字节实测恒定，含义不明）、再刷一次 `0x28` 清单 |
| 取失败（钱庄里不够 / 没有） | `0x0B`、`0x1A`：`64` +「數量不足」、`0x77` |

## 物品信息 C2S 0x71：物品ID(LE32) + 至少 1 字节

回 `0x88`（短帧）= 物品ID + `c8 00 00 00 00`——**对任何 ID（包括不存在的）都是这个**，`c8` 也不随物品变。至少 5 字节载荷才回，4 字节不回。

## 没弄懂

- `0x0B` / `0x77` 里反复出现的 48015（随身钱庄）：为什么存 / 取要回它的"使用确认"和"新增"，是否要求背包里真的有这个物品（原版没检查，
  测试号背包里没有也能存取）。
- 取成功回包 `0x27` 末尾的 `ee dc 00 00`。
- 背包满时取出会怎样（没测，新服务端不检查背包上限）。
- 其余相关的子程序（"自动存入钱庄"：满天书、采集物品）是别处触发的，没碰。
