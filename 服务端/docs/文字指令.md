# 文字指令（C2S 0xC7，`@xxx`）

原版处理函数 `0x6cab50`（4.6 万字节，反编译 6000 行）。客户端把聊天框里 `@xxx` 发上来，载荷 = `04 40` + ASCII 文本（`04` 是聊天子类型，`40` 是 `@`）。
它**不是只给 GM 用的**：大部分是玩家自己用的商城点数 / 门派 / 查询指令，只有「给物品」要求账号 `gm_lvl = 1`。
实现在 `jyserver/commands.py`；`tests/test_commands.py` 的期望值来自原版回包，`tools/cmd_compare.py` 把 11 套场景对原版和新服务端各跑一遍，
**回包和下线后的库状态逐项一致**（`tools/cmd_probe.py` 是手动探针，`tools/db_diff.py` 看一条指令改了库里什么）。

## 已实现

| 指令 | 条件 | 回包 / 效果 |
|---|---|---|
| `@where` | | 自己收 0x04 `02 jyid 地图号文字`（聊天框里一行字） |
| `@kale` | | 传到固定地点 2822 (210, 450)，走传送流程（0x08 + 4 个空帧）。原版另有「战斗中不得瞬移 / 押镖不得瞬移」，新服务端没有这些状态 |
| `@cpw` | | 背包每件物品一行 0x04 `02 jyid "ID﹕名字﹕数量"`（BIG5，分隔符是 `a1 52`），**按内存背包的倒序（最新的在前）** |
| `@tw` + `00`/`01`，`@cxwg`，`@bj` + `00` | 整串完全相等 | 只改原版内存里的开关，**没有回包，库不变**，照做（什么都不做） |
| `@se N` | N 在 −1000..1000 | 回 0x7B `45` = N（有符号），**只改客户端显示**，库里的 `evil_val` 不变；超出范围回 0x1A「善惡在-1000到1000之間」 |
| `@sqsq` | | 回 0x7B `37` = 1000000（杀气显示），库不变 |
| `@wp ID` | 账号 `gm_lvl` = 1，否则**静默**；ID 取 `wp ` 后面**固定 5 个字符**，必须是不带前导 0 的数字 | 物品在物品表（装备 + 药品）里：背包 +1（后面的数量不看），回 0x77 `ID 耐久 01`；否则 0x1A「無此物品」 |
| `@scb N` | `N ≤ 1000`；N < 0 回「不能為負數」；N > 1000 回「單次兌換不得超過1000」；金钱 < N×10 万回「金錢不足﹗」 | 扣 N×10 万金钱、商城点数 +N，回 0x7B `3C` 金钱 → 0x32 `6f` 点数 → 0x14 `03`「儲值點數﹕N點﹗」→ 0x14 `03`「VIP等級﹕7級﹗」。**N = 0 或不是数字 = 只查询**，同样四条 |
| `@mp D` | 商城点数 ≥ 9999（不够回 0x1A「需要商城點數9999才能自由選擇門派」，点数检查在解析数字之前；`@mp` 后面没有字符则静默） | D = `1`…`9` → 门派 / 师承：`1`→10/0，`2`→11/11005，`3`→12/12013，`4`→13/0，`5`→15/15001，`6`→19/19064，`7`→21/21001，`8`→22/22001，`9`→23/23002（只看第一个字符，`@mp 13` = `@mp 1`）；`0` = 不改，照样扣点；别的字符什么都不做。扣 9999 点，回 0x32 `6f` 新点数 → 0x14 `03` 储值点数 → 0x7B `41` 门派 → 0x7B `42` 师承；**全服**收到 0x14 `0e`「土豪﹕<名字>更換了門派﹗」；然后自己收 0x05 + 0x14 `08`「玩家﹕…离開游戲」并被**断开连接**（要重登）。门技等级 / 熟练度不动 |
| `@bpsm` | 免费 | 有门派：补发该门派的「师门标记」（10→50046、11→50044、12→50045、13→33721、15→50049、19→50050、21→50300、22→33558、23→50047；已有则 0x1A「已經有此標記」代替 0x77，不重复）；回 0x7B `49`=0、`4A`=0、0x1A「已經背叛師門」；`school`、`school_skill_lv`、`school_skill_exp` 清零。然后（不论有没有门派）`master` 清零，回 0x7B `42`=0、`41`=0 |
| `@cxg` + 字节 `88` / `89` | 整串相等 | `88`：0x1A「暫停VIP功能﹗」；`89`：0x14 `03`「VIP等級﹕7級﹗」 |
| `@cxg` + 字节 `87`（转生） | 七项属性（str crg wint luk dex agi vit）都 ≥ 100，否则 0x1A「需要全屬性100﹗」 | **满足时没做**，见下 |

**VIP 等级恒为 7**，和商城点数、赞助点数、gm_lvl 都无关（实测改库、换账号都是 7，而且有「暫停VIP功能」）。这也解释了 VIP 回收里那个没查明的条件
`玩家+0x484 > 4`：+0x484 就是 VIP 等级，恒为 7，所以恒成立（见 `docs/丢弃回收交易.md`）。

## 转生（`@cxg\x87`，条件满足时）——原版的效果，没实现

条件满足时原版一次性做了很多事（8617293 号，属性全设 100 后实测）：七项属性重置为 50；`zuidaxue`（最大气血）2000 → 6000；`combat_exp` 0 → 1；
`wuqiqiangdu` 0 → 300、`fangjuqiangdu` 0 → 200；`kf` 表多一行（`kf_id` 3860，`kf_lvl` 10）；回包有 0x68 `14 0f 0a 00…d2 00`、
0x14 `0e`「<名字>進行了轉生﹗」、0xBC `41 <jyid>`、0x1A「重登后生效﹗」。再发一次就是「需要全屬性100﹗」（属性已经是 50）。
具体数值是不是和转生次数有关（第二次转生加多少）没测。

## 对别处的影响

- `@cpw` 的倒序说明：原版重启时背包按库里顺序装进内存，下线时又按内存的倒序写回来（实测每个「装载 → 保存」循环顺序翻一次）；
  新服务端的背包一直是库里顺序，`@cpw` 倒序输出，与原版**一次**循环后的显示一致。
- 登录序列里商城点数（0x32 `6f`）和「儲值點數」公告的格式在 `jyserver/state.py` 里；`@scb` / `@mp` 复用同样的字节。
