## 帧格式

```
明文帧 = 魔数(2) + 长度 + opcode(1) + 参数
  短帧  魔数 F4 44，长度 1 字节   —— 抓包旧文档称「格式B」，loginp 笔记称「格式A」
  长帧  魔数 F5 B3，长度 2 字节LE —— 抓包旧文档称「格式A」，loginp 笔记称「格式B」
  长度 = 整帧字节数（含魔数）
S2C 线路 = XOR(key, 明文帧)
C2S 线路 = F6 11 <seq> + XOR(key, 明文帧)
```

| 结论 | 等级 |
|---|---|
| 密钥写在帧头：短帧 `key = A^F4 = B^44`，长帧 `key = A^F5 = B^B3`（A、B 是线路前两字节） | 实测（C2S 81/81，S2C 64/64） |
| C2S 帧长度字段把 A、B 两字节计入，C2S 总包长 = 3 + 长度 | 实测（握手样本 20 = 3 + 17） |
| 同一方向短帧长帧都会出现，由原服务端按包类型选；客户端两种都接受 | 实测（0x08 用长帧，0x06 用短帧） |
| 一个 TCP 块可含多帧（粘包） | 实测 |
| 发送端按消息长度选格式：消息(opcode+参数) ≤ 250 用短帧，否则长帧 | 反编译（loginp 0x9dabc8），与原服务端「按类型选」不矛盾 |
| 握手：C2S 首包密钥 `0x9E`；S2C 首包密钥 `0x9F`，短帧、整帧 34 字节，线路上多 1 个字节 | **实测**（2026-10 本机原服务端 + 模拟客户端，响应与旧抓包逐字节一致）；响应本身是服务端里一条固定常量文本 |
| 握手成功后服务端把该玩家的密钥设为 `0x7D`；此后 **S2C 帧都用 0x7D** | 反编译（`PUSH 0x7d` 写入 `player+0x10c`）+ **实测**（登录序列 19 帧全部 key=0x7D） |
| **C2S 密钥 = `0x7D XOR 序号`（首包 seq=1 固定 `0x9E`）**；服务端并不读帧头里的密钥，而是由序号算出 | **实测**：序号 2/3/4/5 的探针，只有 `0x7F/0x7E/0x79/0x78` 能让服务端处理该帧；用固定 `0x7D` 的帧全被静默忽略 |
| 相同序号的两帧会被断开（防重放，`player+0x344` 存上次序号） | 反编译（`0x5fe75c`） |
| 之后默认密钥 `0x7D`，服务端重启前后不变 | 实测（旧文档） |
| 密钥会中途更换；规则：收到类型 `0x99` 且载荷首字节 `0x04` 的帧，后 4 字节为种子，`key = (138·b0 + 307·b1 + 93·b2 + 78·b3 + 145) mod 217` | **反编译 + 真实流量校准**：反编译得常数项 163，真实流量（种子 `a2bc2837`→0x7d、`0eaea531`→0x0e）校准为 145 |

**实测验证（2026-10，新建角色流程）**：还没有角色的账号登录时，原版回的握手载荷带种子 `a2 bc 08 5f`，`derive_key` = 0x34；
此后 S2C 帧的密钥确实是 0x34，C2S 帧也必须用 `0x34 XOR 序号`（用 0x7D 的原版不理）。公式（常数项 145）有了第二个实测点，
同时说明「握手之后一律 0x7D」只对已有角色的账号成立。见 docs/新建角色.md。

**服务端周期性换密钥（2026-10 实测）**：已有角色的号登录后，每隔几十秒会收到 `0x33` + `0x99 04 <种子>`；客户端必须把 C2S 密钥基数换成
`derive_key(种子)`，否则原版静默忽略之后的指令（种子 `0e ae a5 31/33/36` 都验证过）。详见 docs/药品效果.md。新服务端不发这对帧。

补充（第二轮）：服务端.exe 内置了 10 条 `99 04 <种子>` 密钥更换帧（`data/s2c_templates.json`），
种子 `0e ae a5 31`…`38` 等，按公式算出的密钥为 `0x20 0x6e 0xbc 0x31 0x7f 0xcd 0x42 0x90`，另有 `29 62 3e b6`→`0x64`、`21 3d b0 96`→`0x53`。
这证实了「服务端会发 99 04 帧来换密钥」的机制，但**抓包里观察到的切换是 `0x7D → 0x0E`，这 10 个种子算出的密钥里没有 `0x0E`**，
所以公式本身仍然没有被真实流量验证（也可能抓包那次用的是别的种子）。M1 抓包时要专门核对。

编码侧的风险：**解码不需要状态，但编码必须用客户端当前期望的密钥**。如果密钥更换规则有误，
客户端会解出乱码并断开。M1 要用真实客户端验证这一点。

## 其他已知事实

- 网络实体 ID == 数据库 `jyid`（实测）。
- 战斗由客户端主导：怪的出招也由客户端上报，服务端不算战斗（实测，见旧文档 0xD7 一节）。
- 线上中文是 BIG5 繁体，数据库和 CSV 是 GBK 简体，服务端下发前要转换（实测）。字形转换（简→繁）还没做。
- 密码在 `account.password` 里是每字符 hex 的可逆编码；登录包里没有密码，服务端信任 C2S `0x01` 带的账号 ID（实测）。
- 原服务端强制单点登录：旧会话角色还在内存里时会在第 3 个包后断开连接（实测）。
- 客户端有 IP 校验，拒绝回环地址，会读 `WatchIP.txt`；`server.ini` 要填局域网 IP 并存成 GBK（实测）。
- `server.ini` 里的是更新服务器地址，不是游戏服务器地址（反编译）。游戏服务器端口 6731（实测）。
