# 战斗：初步探测（早期记录；已有单人打怪实现，见 `docs/战斗.md`）

方法：用 `tools/pseudo_branches.py`、`tools/condense_pseudo.py`、`tools/flow_outline.py` 把 `0x40db88`（"进入战斗"，94 KB）
的骨架画出来，再用模拟客户端对原版发包看回包。**没有真实客户端的战斗抓包**（旧项目的抓包文件已不在），所以下面的载荷布局
是反编译 + 试探得到的，不是真实客户端会发的内容。**新服务端目前没有任何战斗功能。**

## 结构

- 战斗相关的 C2S 指令（`30 D3 D4 D7 D8 DA DE DF E3 E4 E5 E6 F9`…）在分发函数 `0x5f8f04` 里挤在一起，全部走**同一个**函数 `0x40db88`，
  它在内部再按令牌 `T[3]`（opcode）逐个比较字符串分支（`tools/pseudo_branches.py` 能列出：`30` 在伪代码第 912 行，`DA/D7/DF/D8/F9/E5/E6/E4/D3/E3/DE/D4`
  依次在 3404–4682 行）。
- 函数里夹着大量别的东西：反作弊（`禁止快速进战斗`、`禁止开快招`、`禁止开快速集气`、攻击间隔小于 0x514 就踢）、
  战役事件（烟雨楼 / 少室山 / 黑木崖 / 五毒教 / 终南山 / 武当山）、死亡惩罚（替身娃娃、实战未到 100000 不掉级、武功随机掉一级）、
  狂状态、组队参战（全局数组 `DAT_00dd8510`）。这是整个游戏里最大的一块。

## 实测到的往返（单人，对原版）

| C2S | S2C 回包 | 备注 |
|---|---|---|
| `0x30` + 实体ID(LE32) + 19 字节（零即可）；实体ID = 怪物实例序号×100000 + `MOB数据.csv` 的 mob_id，如 100038166 = 倭寇第 1000 号实例 | `0xD1`(24) `01 00 <实体ID> 00×10 <随机数 LE32，实测 8/25/51/70> 00×4`；`0x82`(长) `<jyid> 02 00`；`0xDC`(23) `01 00 <jyid> 01 00 00 00 <当前气血 LE32> 00…` | 实体ID < 10000001（直接写 mob_id）时只回 `0xD5` `01 00 <jyid> <类型 LE16，实测 55 09>`（我方名单），不进入战斗 |
| `0xD4` + 实体ID(LE32) + 2 字节坐标 + 1 字节密钥 + … | `0xD4` `<实体ID> <b4^b6> <b5^b6>` | 服务端把客户端上报的两个坐标字节用载荷第 6 字节异或后还原（旧笔记里"每场固定常量异或"就是这个） |
| `0xD8`（14 字节） | `0xD8`(长) `01`（空清单） | |
| `0xE5` + jyid(LE32) + 1 字节 | `0x81`(长) `01`（气血为 0 则 `02`）、`0x82` `<jyid> 00 00`、`0xE6` `<jyid>`、`0x7B 18 01 <当前气血>` | 气血 ≤ 1 的号结束战斗时被判死亡：另发 `0x14` 提示，`0x81 02` |
| `0xE3`（进战，`<jyid> 列 行 01 尾字节`） | **没有回包**（试了 07 / 无尾字节 / 未先 0x30） | 旧笔记说它后面跟两个 `0xD5` 名单，我这里没复现 |
| `0xD7`（28 字节出招，格式见旧笔记） | **没有回包**，24 次连发（间隔 1.4 秒）也没有伤害、死亡或掉落 | 对怪的伤害到底是谁算、怎么触发 `0xE4/0x77/0xE8` 掉落三连，没查清 |

## 没弄懂 / 风险

- 怪物的血量、伤害由谁计算，掉落怎么触发。旧笔记里"玩家打死怪那一刻，客户端没发任何带伤害的包，是服务端发的掉落三连"；
  我这边发出去的 `0xD7` 没有任何效果，说明触发条件里还有我没满足的前提（`0xE3` 之后的状态？别的指令？）。
- 对新建的满血号（9999041，出生在地图 3304）发 `0x30` 没有回包；而已有的号（地图 2200 / 2801）有。可能跟地图、怪物所属地图、
  上线后经过的时间有关，没查。
- **原版服务端很脆**：试探时发了几个畸形战斗包（含断开时仍在战斗状态）后，原版进程直接崩溃过一次（需要手动重启）。
  之后凡是做战斗对照实验，都要准备好随时重启原版。
- 没有真实客户端的战斗抓包，载荷布局都只能靠反编译 + 试探推；而这一块反作弊分支很多，**很容易做出"自己的服务端自洽、
  真实客户端却不认"的实现**。

## 建议

战斗需要比前面任何模块都多得多的逆向，而且最好有真实客户端的抓包做基准。如果能找一台能跑客户端的机器抓一份"遇怪 → 打死 → 掉落 → 结束"
的完整流量，后面的工作量和风险都会小很多。在那之前，更划算的是先把别的能验证的部分做完（私聊/组织聊天、定时换密钥帧、定时存档、
出售给商人），再回来做战斗。
